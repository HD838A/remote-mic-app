# Onboarding 重新运行后无法可靠完成并进入可用主页面

- 时间：2026-09-20
- 状态：调查中，产品边界已确认；等待最新 `origin/main` 复现、日志核对与后续修复
- 影响范围：macOS；已完成过 Onboarding、随后从“关于/设置”主动重新运行设置向导的用户
- 功能点：Onboarding 重跑、语音测试、完成门禁、运行时就绪
- 简单描述：用户按要求重新完成 Onboarding 时，流程可能卡死或无法到达完成态，因而不能进入已经完全可用的主页面。
- 原始记录：[GitHub Issue #456](https://github.com/HD838A/remote-mic-app/issues/456)，现场为 macOS 15、SayAll `1.9.21 (175)`；Issue 未附运行日志。

## 产品边界

以下行为是产品设计，不属于本 Bug：

- Onboarding 不提供取消、跳过或“稍后继续”入口。
- 欢迎页没有“上一步”按钮。
- 用户主动重新运行 Onboarding 后，必须重新完成必要验证，才能返回主页面。
- Onboarding 未完成时，关闭 App、重启系统或重新安装 App 后仍恢复到未完成流程；重新安装不会自动清除已有 `UserDefaults`。
- 不得通过恢复旧的 `onboarding.completedVersion`、保留完成标记或增加退出入口绕过流程。

本 Bug 的判断标准不是“能否退出向导”，而是：用户按照页面指引快速、正确地完成必要操作时，流程必须能够稳定推进；进入主页面时，控制、语音键、音频输出和运行时必须已经可用。

## 观察

### 用户现场

- 用户从“关于/设置”选择“重新运行设置向导”。
- 用户反馈向导流程无法完成，并称停在向导页面后进程可能卡死。
- 由于向导未完成，后续启动仍恢复到向导；这部分符合产品设计，不能单独作为错误证据。
- Issue 中的救急命令直接写入完成标记，只能作为现场恢复手段，不能作为正式修复：

  ```sh
  defaults write com.hd838a.RemoteMic onboarding.completedVersion -int 1
  defaults write com.hd838a.RemoteMic onboarding.step -string complete
  ```

### 当前代码

- `AppSettings.restartOnboarding()` 将步骤设为 `.welcome`、完成版本设为 `0`，并重置向导选择，使重跑流程重新受全部完成门禁约束。
- `RemoteMicRootView` 只有在 `settings.isOnboardingComplete == true` 时才显示主设置页。
- `OnboardingFlowPolicy.canContinue()` 依次检查语音工具、权限、控制来源、真实普通按键、音频路线、真实语音样本、会话结束、第三方文字以及三个不同普通按键。
- 完成页会再次检查权限、控制来源连接和音频路线；只有用户点击完成后，`completeOnboarding()` 才写入完成版本并切换到主页面。
- 上述门禁方向符合产品要求，不应通过增加取消或跳过路径修复。

## 假设

### H1：语音测试页的 SwiftUI 订阅循环阻止流程完成

- 支持证据：PR #468 已确认 `model.$isStreaming.removeDuplicates()` 在视图重算时反复重订阅，持续触发 `beginVoiceAttempt()`；现场表现包括高 CPU、日志高速增长、页面失去响应和无法完成语音测试。
- 冲突证据：#456 报告的是 build 175，而 #468 的完整日志来自 build 227；#456 没有日志，不能确认是同一根因。
- 当前状态：#468 已合入 `origin/main`，最新主线已恢复为 `model.$isStreaming`。需要使用最新主线执行原始重跑流程，确认卡死是否消失。

### H2：某个真实能力门禁没有在正确操作后更新

- 支持证据：重跑流程依赖权限刷新、BLE/HID、音频输出、语音 attempt 和第三方文字等多个异步状态；任一状态未刷新都会使“继续”保持禁用。
- 冲突证据：当前每个页面已有针对已知失败的刷新和恢复逻辑，尚无 #456 的日志能定位具体门禁。
- 验证方式：按步骤记录 `ONBOARDING STEP`、权限、连接、HID、音频、`VOICE_ATTEMPT` 和完成页运行时状态，找出最后一个已确认成功事件和第一个未满足门禁。

### H3：正确完成页面检查后，运行时应用尚未完成即切换主页面

- 支持证据：向导会触发 HID 与音频配置，部分操作包含异步系统状态；产品要求进入主页面时已经完全可用，而不只是配置已写入。
- 冲突证据：完成页当前会重新检查连接和音频 Ready，且流程已真实通过语音与普通按键；尚无证据证明主页面切换过早。
- 验证方式：完成前后连续验证生产 HID、语音键、音频绑定和控制来源状态，区分“设置已提交”和“运行时已生效”。

## 当前结论

- “没有取消入口”“欢迎页不能返回”“未完成后重启仍进入向导”均为设计要求，不应修改。
- #456 应收敛为一个完成性 Bug：用户正确操作时，Onboarding 仍可能卡死或无法满足某个门禁，导致不能完成流程。
- 当前最强根因候选是 #468 已修复的语音 attempt 失控循环，但由于现场版本和日志证据不一致，尚不能把 #456 标记为已修复。
- 在最新 `origin/main` 重新复现并取得日志前，不编写新的业务修复，避免把产品门禁误删成“修复”。

## 后续修复约束

后续实现必须满足：

1. 不增加取消、跳过、稍后继续或恢复旧完成标记的旁路。
2. 正确操作后每一步都能在合理时间内观察到真实状态并继续。
3. 不用“收到事件”“已入队”或用户勾选代替最终功能成功。
4. 进入主页面前必须确认生产运行时已经具备当前控制来源、语音键和音频路线。
5. 重跑不得清除现有连接资料、按键映射、音频选择和其他无关设置。
6. 可以保留仍然有效的既有选择以减少重复操作，但真实权限、连接、音频、语音和按键验证仍必须重新完成。

## 后续复现与验证计划

1. 基于最新 `origin/main` 构建测试包，从已完成状态点击“重新运行设置向导”。
2. 分别执行实体遥控器、iPhone App 和网页版三条控制来源流程。
3. 记录每一步的进入、成功、失败、重试和最终结果，重点检查语音测试页是否出现 attempt 重复、CPU 升高或日志增长。
4. 使用真实权限、真实控制设备、支持的虚拟音频设备和真实第三方语音工具完成一次端到端文字上屏。
5. 在完成按钮可点击时再次核对权限、连接、音频绑定与运行时 Ready。
6. 进入主页面后立即执行一次普通按键和一次语音会话，证明 App 已完全可用。
