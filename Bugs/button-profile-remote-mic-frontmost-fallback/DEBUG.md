# 无线麦前台仍沿用上一套专用方案

## 观察

- 自动模式下，先让网易云等目标 App 的专用方案生效，再打开无线麦SayAll.app，遥控器仍执行上一套专用方案。
- 这会让用户在无线麦页面测试或操作时意外控制上一应用，与“其他 App 使用默认方案”的理解冲突。
- “设置按键”步骤仍需要拦截实体键用于选键，但这是执行路由门禁，不应依赖保留上一套专用方案。

## 假设

1. 自动解析器把无线麦 Bundle ID 与 `nil`、空 Bundle ID 放在同一保持当前分支。
2. 前台 App 监听没有发出无线麦的 Bundle ID。
3. 宿主页打开时没有把前台变化传给私有模块。

## 复现实验

- 使用可注入前台 App 监听器执行：Codex 前台 → 无线麦前台 → `nil` → Codex 前台。
- 修复前测试在“无线麦前台应回默认方案”处失败，证明问题存在于私有方案解析器，而不是 NSWorkspace 通知或宿主转发。

## 根因

`resolveActiveButtonProfile` 的 guard 把无线麦 Bundle ID 与 `nil`、空字符串放进同一个分支。该分支只有在当前方案尚未初始化时才设置默认方案，否则保留上一个专用方案。注入监听器已经发出了无线麦 Bundle ID，因此假设 1 成立，假设 2、3 排除。

## 修复与验证

- 将无线麦 Bundle ID 从“未知前台状态”分支分离，明确设置默认方案。
- `nil` 和空 Bundle ID 继续保持当前方案，避免锁屏或系统切换瞬间产生无意义跳变。
- 原始自动切换测试修复前在无线麦步骤失败，修改后通过，并覆盖再次回到目标 App 时恢复专用方案。
- “设置按键”步骤的宿主路由测试继续验证只选键不执行；此能力不再依赖保留上一套专用方案。
