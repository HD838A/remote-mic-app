# 注入按键驱动系统听写：Fn 无效，两次 Control 有效

- 时间：2026-11-08
- 状态：**调研完成，无产品代码改动**；结论用于判断「由 App 发送快捷键驱动系统听写」是否可行
- 基线：公开仓库 `origin/main` `37511759`（2026-11-08）
- 环境：macOS 27.0.1（26A434）、Apple Silicon、辅助功能已授权、听写语言含中文、听写麦克风设为 `自动（SayAll）`
- 影响范围：任何计划注入按键触发系统听写的实现；不影响豆包、微信、Typeless、Vokie 的现有驱动方式
- 功能点：语音键、系统听写（`com.apple.inputmethod.ironwood`）、输入源准备

## 一、结论

同一个注入方式（`CGEventPost` 到 `cghidEventTap`），不同按键的结果完全不同：

| 听写快捷键配置 | 注入的按键 | 结果 |
| --- | --- | --- |
| 按下 🌐 | 单击 Fn（keycode 63，flags `0x800000`） | **无效** |
| 连按两下 🌐 | 双击 Fn（间隔 80 ms） | **无效** |
| 连按两下 🌐 | 同上改用 `cgSessionEventTap` | **无效** |
| 连按两下 🌐 | 同上改用 `combinedSessionState` 事件源 | **无效** |
| **连按两下 Control** | **双击 Control（keycode 59，按住 60 ms、间隔 80 ms）** | **有效，稳定启停** |
| 任意 | 单次 Control | 无效（不会误触发） |

也就是说：被过滤的是 **Fn 这一个键**，不是「合成修饰键双击」这一整类。用 Control 走同一条注入通道可以正常驱动系统听写，这正是 [PR #326](https://github.com/HD838A/remote-mic-app/pull/326) 采用的路径。

## 二、Control 路径的实测细节

配置为「连按两下 Control」后，用 `CGEventPost` 发送两次左 Control（keycode 59，按下时 `flags = maskControl`，抬起时清空）：

- **启动**：听写界面在 0.1～0.5 s 内出现，随后稳定保持；连续三轮启停都成功。
- **停止**：再发同样两次 Control，约 0.5 s 后界面消失。
- **单次 Control 不触发**：从空闲状态发一次，界面无任何变化。
- **间隔容忍范围**：按住 60 ms 时，间隔 60 / 150 / 250 / 400 ms 都能触发，600 ms 不触发；按住 20 ms、间隔 60 ms 也能触发。窗口与系统双击阈值一致，约 500 ms 以内。
- **无修饰键残留**：每轮结束后 `CGEventSource.flagsState(.combinedSessionState)` 的 `maskControl` 均为 `false`，不会像按住那样影响后续键盘输入。
- **未验证**：真实语音是否被识别成文字（测试期间没有语音输入），以及首字延迟与定稿延迟。

## 三、系统听写的触发机制

听写快捷键菜单共 7 项：**按下 🌐**、连按两下 Control、连按两下 🌐、连按两下右 Command、连按两下左 Command、连按两下任一 Command、自定义…。它们落在两处配置：

| 界面选项 | 配置位置 |
| --- | --- |
| 按下 🌐 | `com.apple.HIToolbox` 的 `AppleFnUsageType = 3`（Fn 键用途 = 开始听写） |
| 连按两下某修饰键 | `com.apple.symbolichotkeys` 的 `AppleSymbolicHotKeys` 第 `164` 项，`type = modifier` + 修饰位 |
| 自定义… | 同一项，`type = standard` + 键码与修饰位 |

实测到的两个坑：

- **选「按下 🌐」不会写回 `AppleFnUsageType`**：把快捷键改成「连按两下 Control」后系统删除了 `AppleFnUsageType`；再选回「按下 🌐」时它仍然为空，`164` 变成 `enabled = 0` 的占位项。这两处是独立配置，恢复时必须分别写回。
- **`enabled = 1` 不代表该项被选中**：把快捷键设为「按下 🌐」时，`164` 仍保留 `enabled = 1`、`type = modifier`、`param0 = 0x800000` 的 Fn 定义。判断当前生效方式必须同时读 `AppleFnUsageType`。
- **`CopySymbolicHotKeys` 读不到听写**：本机返回 234 条里没有任何带 Fn 标志的条目，且数组下标与 symbolic ID 不对应。读取只能用 `CFPreferencesCopyAppValue`。

听写开关与麦克风：

- 只把 `com.apple.assistant.support` 的 `Dictation Enabled` 写成 `1` 不足以启用，系统仍会弹「你要启用"听写"吗？」确认框，必须真人点「好」。应用无法代用户完成启用。
- 麦克风选项没有可读的偏好键，但可以用辅助功能读到当前值：本机显示 `自动（SayAll）`，说明用户可以把听写麦克风指向虚拟声卡。

## 四、判定方法

听写是否真的在收音，用两个互相独立的信号判定，任一为真即视为已启动：

1. **窗口特征**：菜单栏出现 2 个 `Window Server / StatusIndicator`（28×28，右上角），且前台 App 名下出现一个 `layer = 3`、约 84×77 的浮窗（麦克风 HUD）。空闲状态下两者均为 0。
2. **菜单项标题**：前台 App 的「编辑」菜单在「开始听写」与「停止听写」之间切换。

对照组：用辅助功能对「编辑 > 开始听写」执行 `AXPress`，浮窗在 0.04 s 内出现；再点一次变「停止听写」后浮窗消失。

## 五、对「支持系统听写」方案的影响

- **Fn 路径不成立**：用户若把快捷键配成「按下 🌐」或「连按两下 🌐」，App 注入的 Fn 一律被忽略。这条与用户实际配置直接冲突，不能再按「读用户配置后原样重放」设计。
- **Control 路径成立**：把快捷键配成「连按两下 Control」后，注入的两次 Control 可以稳定启停听写。#326 的按键层假设因此得到验证；它剩下的风险不在注入，而在音频时序（首字、尾音）、250 ms 预铺是否足够、真实文字上屏和连续会话。
- **代价是要求用户改配置**：这条路径必须让用户在系统设置里把听写快捷键改为「连按两下 Control」，与「不改用户配置」的约束冲突，需要产品或引导层面明确取舍。
- 另一条被验证可用的程序化驱动是点击「编辑 > 开始听写」菜单项，但它依赖前台 App 暴露该菜单（系统 App 有，多数 Chromium/Electron 应用没有），覆盖面和可靠性都不足以支撑「任意输入框可用」。

## 六、未覆盖边界

- 连按两下 Command、自定义组合键是否同样接受合成事件（未逐一验证；已证 Fn 被过滤、Control 可用）。
- 真实语音的文字上屏、首字延迟、定稿延迟、静音自动结束，以及「用户中途点完成」导致的状态错位。
- 长会话中途重复注入是否会与听写自身的状态机冲突。

## 七、复现步骤

1. 在系统设置中开启听写并完成首次确认，把快捷键设为「连按两下 Control」。
2. 用一个空白文本窗口作为目标，记录窗口基线（菜单栏指示器数量应为 0）。
3. 通过 `CGEventPost` 发送两次左 Control（keycode 59，按住 60 ms、间隔 80 ms），随后 3 秒内每 150 ms 采样第四节的两个信号；预期听写界面出现，再发一次同样序列则关闭。
4. 把快捷键改为「按下 🌐」后重复发送一次 Fn，预期无任何反应。
5. 结束后把快捷键与 Fn 键用途分别写回原值（注意第三节的第一个坑），并确认听写开关恢复。

用于验证的临时工具只保留在仓库外的工作目录，未进入版本控制。
