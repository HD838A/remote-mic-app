## 错误证据与边界

用户反馈正常松键会少最后约 2–3 秒；说完后继续按住约 3 秒的对照结尾完整。
一次会话墙钟时长 19,351 ms，收到 282,240 个 16 kHz 样本，即约 17.640 秒；
这种差值包含启动、采集、无线传输等未知因素，不能把它全部归因于尾音丢失。
该次没有入队失败，STOP 时 pending_buffers=3，软件键 UP 在播放排空前约 47 ms。

确定的主机侧缺陷：`bluetoothBridgeDidStopVoice` 先调用
`releaseVoiceKeyIfNeeded`，之后才观察播放队列排空。按住收音的消费者可能在软件键
UP 后停止接收，因而即使 SayAll 最终播放完毕，消费者仍会失去在途尾部。
此顺序缺陷本身不能解释全部 2–3 秒差值；本地候选不宣称修复遥控器采集或无线层缺口，
也不宣称 CoreAudio dataPlayedBack 等于第三方 ASR 已消费。

## 与既有修复的关系

旧 PR #320 提出了类似顺序修复，后因 #523 合入而关闭。#523 解决共享排空等待
被中断时丢回调的问题，但当前主线普通蓝牙 STOP 仍提前释放软件键。
本候选复用该共享排空 API，仅新增蓝牙软件键的释放等待与 generation 隔离，
不恢复旧 PR 的共享队列取消逻辑。活动 PR #323（空闲音频占用）、#328（移动 Fn Tap）、
#766（一分钟续录）分别处理不同范围，可能在 BridgeAppModel 有代码重叠。

## 最小修复候选

- 仅普通 Bluetooth 软件修饰键路径等待 `AudioOutput.endSessionAfterDraining`；
  空队列立即释放，不增加固定等待，不改变首包触发。
- 排空期间保留逻辑语音会话和虚拟输出，避免提前收尾或挂起释放设备。
- 快速再次按下使旧等待失效，保留同一 owner 的键保持状态；不取消共享输出队列。
- 断连和 App stop 取消旧等待，继续现有强制清理；旧回调不能释放新会话。
- 使用既有 750 ms 排空上限；超时由现有 AudioOutput 记录 forced 和中断样本，
  不伪装成正常完成。没有在正常路径新增 flush。
- 硬件 Fn 与 Fn Tap 路径维持原有处理。新日志只记录短生命周期编号、阶段和结果。
