# 小米在线时 SayAll 冷启动漏连 T1

## 现象与证据

Build 451 在 macOS 蓝牙设置显示 T1 已连接、小米也在线的情况下启动。小米自动就绪，T1 留在「连接过的设备」。日志中 T1 的 `REMOTE CARD_READINESS` 保持 `bridge=missing_bridge`。点击 T1 卡片上的「连接」后，现有蓝牙标识正常完成握手，按键和语音都变为就绪。保持系统配对并重开应用，可以复现。

小米的 HID 监视器在启动时创建目标桥，连接过程按设计抑制自动共享发现。T1 的输入监视器在自己的蓝牙桥就绪后才建立，因此没有与小米相同的启动信号。现场只读验证确认 T1 的活动 BLE HID 服务提供了与保存档案一致的 `PhysicalDeviceUniqueID`。

## 修复

应用启动蓝牙连接时，按 T1 的厂商、产品与 BLE 传输属性查询当前 HID 服务。只对物理 UUID 与保存档案完全匹配、且尚未创建目标桥的 T1，调用既有的有限自动恢复路径。离线档案不尝试连接，共享发现的抑制条件不变。

## 验证结果与边界

- 恢复蓝牙、输入监控和辅助功能后，确认系统蓝牙中 T1 已在线。退出并重新打开 Build 452 两次，期间未点击设备的「连接」。两轮连接页均显示小米和 T1 在线。日志显示 T1 在各次进程启动后约 3.85 秒和 4.86 秒按键与语音就绪，两只设备通过 `manual=false` 恢复。
- 权限刚恢复后的首次启动仍观察到一次 `bridge=missing_bridge`。系统已枚举 T1 后的两轮通过，验证范围是 macOS 已连接并能提供对应 HID 身份后的应用冷启动。T1 在应用启动之后才被系统枚举的情况需要单独验证。
- `BluetoothLifecycleTests.startupRestoresSystemConnectedT1EvenWhenDiscoveryIsSuppressed` 检查启动路径只接入匹配的在线档案，并且早于可被抑制的共享发现。使用相同条件单独检查源码时，修复前失败，修复后通过。`scripts/test.sh` 的 65 项自检通过，应用编译和签名通过。当前 Mac 的 Command Line Tools 缺少 `Testing` 模块，Swift Testing 套件由 CI 运行。
- 同时更新同一 T1 改动引起的 CI 断言，覆盖 T1 指定的蓝牙发现参数、按键高亮和离线画布入口。将现有四个测试及新增冷启动测试里的实际断言抽出，在本机以 Swift 执行，五项通过。
