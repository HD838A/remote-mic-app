# macOS 听写仍需手动触发

## 现场复现

- 版本为无线麦 1.9.18（171），设备为小米 RC003，语音输出选择 `MiRemoteV 2ch`。
- macOS 听写已开启，语言为普通话，快捷键设为连续按两下 Control。
- 输入框获得焦点后，只按住遥控器语音键说话并松开。无线麦显示语音键、声音和音频输出均正常，输入框没有文字。
- 先在 Mac 键盘连续按两下 Control，再按住遥控器语音键说话，松开后再次连续按两下 Control。相同输入框能够出现文字。

## 日志结论

2026 年 8 月 31 日 18 时 28 分左右的多次现场记录均包含完整的 `STREAM_START → AUDIO → STREAM_STOP`。音频被路由到 `MiRemoteV 2ch`，首批样本返回 `accepted=true`，结束后播放队列完成排空。日志没有显示蓝牙断流、解码失败或虚拟音频输出失败。

这组对照把故障范围限定在语音工具的启动和停止动作。音频路径已经通过同一台 Mac、同一个遥控器和同一个输入框完成实际验证。

## 根因

无线麦 1.9.18 默认把 RC003 的 F5 语音键映射为一次 Fn 长按。macOS 听写当前要求连续按两下 Control。现有设置没有能够把遥控器的一次按下和释放转换成两次 Control 点按的模式，因此听写不会自动启动。

Typeless 的 Fn 点按模式也不能直接替代。它在语音开始和结束时各发送一次 Fn 点按，目标快捷键和事件数量都与 macOS 听写不同。

## 修复目标

- 新增 macOS 听写触发模式，并明确该模式配合系统的连续按两下 Control 快捷键使用。
- 实体遥控器语音键按下后尽快发送两次左 Control 点按，随后回放已缓存的开头音频。
- 遥控器松开后先把尾音排空，再发送两次左 Control 点按并结束听写。
- 不增加语音键双击、长按判定或等待窗口，不改变默认 Fn、Command 和 Typeless 路径。
- 辅助功能权限、HID 中和失败、断连、快速按下释放及连续会话继续安全回退。

## 修复结果

- 新增默认关闭的 macOS 听写模式，并与 Fn 点按模式互斥。
- 开始和停止各发送两次左 Control。每次按住 60 毫秒，两次之间等待 80 毫秒。
- 开场双击完成后先写入 4,000 个 16 kHz 静音样本，再播放预卷音频，给系统听写留出约 250 毫秒启动时间。
- 只有实体小米 RC003 的蓝牙语音路径调用该模式。RC001、未识别型号、iPhone、Apple Watch 和网页版不会发送 Control 双击。
- 首次连接且型号尚未确认时，只在 macOS 听写已开启的情况下等待型号读取完成；普通 Fn、Command 和 Typeless 路径保持原连接时序。关闭听写会立即解除等待，型号读取明确失败时保持未识别并拒绝发送 Control。
- 运行期间的异常清理沿用 60 毫秒按住和 80 毫秒间隔。App 正在退出时只做同步的尽力释放，避免退出后留下按住状态，不把退出期按键节奏表述为系统听写成功。
- 日志使用同一 `trace` 关联开始请求、停止请求、失败和外部观察边界。macOS 最终是否把文字写入输入框无法由公开接口可靠确认，因此明确记录 `diagnostic_boundary=macos_dictation_text_unobservable`。

## 验证边界

新增的自动化用例覆盖双 Control 事件顺序、辅助功能权限门、实体遥控器 HID 中和、首次型号读取顺序、开头预卷、结尾排空、快速按下释放、连续会话、断连清理、配置兼容、取消终态和旧路径回归。

本机只有 Swift 6.1.2 Command Line Tools，而项目要求 Swift tools 6.2，因此这些用例和完整构建没有在本机运行；本地只完成逐文件语法、资源格式、补丁格式和仓库边界检查。最终可用性仍需在项目 CI 和合规签名版本中验证，并用 RC003 与 macOS 听写完成真实文字上屏测试。
