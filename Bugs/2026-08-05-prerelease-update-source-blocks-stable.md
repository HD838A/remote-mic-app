# 预发布更新源不可用时阻止正式更新

- 时间：2026-08-05
- 状态：已修复
- 影响范围：启用“检查预发布版本”的 Mac App
- 功能点：Sparkle 更新通道回退
- 简单描述：候选版本不存在、过期或网络失败时，预发布更新源会阻止正式版更新继续被检测。
- 原始记录：中英文版本历史；修复提交 41b971b

## 详细过程

旧逻辑把预发布候选源视为必须成功的前置步骤。修复后候选不存在、过期、网络超时或暂时不可用都会静默回退正式更新源，不再弹错误或阻止稳定更新；同时增加构建与行为测试。历史调查未单独保存，本文不补写无法从提交恢复的现场细节。

## 1.8.7 回归审计

### 复现与正常边界

使用 Sparkle 2.9.4 官方 CLI 对已发布版本的固定 appcast 执行探测，不修改 App 的持久化更新设置：

- `1.7.8 → 1.8.3` 正式源：检测到更新。
- `1.7.8 → 1.8.5` 预发布源：检测到更新。
- `1.8.3 → 1.8.3` 正式源：无更新，Sparkle 以退出码 `4` 正常结束。
- `1.8.3 → 1.8.5` 预发布源：检测到更新。
- `1.8.5 → 1.8.3 / 1.8.5`：均无更新，Sparkle 以退出码 `4` 正常结束。

未复现正式源或预发布源无法识别跨版本更新的问题。退出码 `4` 仅表示当前源没有更高版本，不属于失败。

### 代码与根因边界

预发布检查先从 GitHub Release 资产中解析最新非草稿 `appcast.xml`。解析失败时必须清除之前缓存的预发布 URL，再让 Sparkle 使用 `Info.plist` 中的稳定 `SUFeedURL`。`1.8.7` 的关于页信息检查和用户主动更新共用同一长期 Sparkle updater，不创建临时 updater；切换通道会重置当前更新周期和旧的页面结果，再探测新通道。

### 修复与验证

本次没有发现新的传输层根因，因此没有修改 Sparkle 安装流程。新增的页面状态处理只解决“切换通道后仍显示旧结果”的界面风险，并继续保留候选源失败时静默回退稳定源的既有修复。发布后还必须使用固定 `v1.8.7` appcast 完成至少一次 `1.8.3 → 1.8.7` 真实安装，探测结果不能替代安装验收。
