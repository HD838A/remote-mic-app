# 注入的 Fn 事件无法驱动系统听写

- 时间：2026-11-08
- 状态：**调研完成，结论用于否决「由 App 发送快捷键驱动系统听写」的方案；本记录不含产品代码改动**
- 基线：公开仓库 `origin/main` `37511759`（2026-11-08）
- 环境：macOS 27.0.1（26A434）、Apple Silicon、辅助功能已授权、`AppleFnUsageType = 3`、听写语言含中文
- 影响范围：任何计划用「按下 🌐」或「连按两下 🌐」触发系统听写的实现；不影响现有豆包、微信、Typeless、Vokie 的驱动方式
- 功能点：语音键、系统听写（`com.apple.inputmethod.ironwood`）、输入源准备

## 一、结论

在 macOS 27 上，用 `CGEventPost` 注入的 Fn 事件**不会**触发系统听写：

| 触发方式 | 结果 |
| --- | --- |
| 注入单击 Fn（keycode 63，flags `0x800000`，`cghidEventTap`） | 无效 |
| 注入双击 Fn（两次间隔 80 ms） | 无效 |
| 同上改用 `cgSessionEventTap` 投递 | 无效 |
| 同上改用 `combinedSessionState` 事件源 | 无效 |
| 辅助功能点击「编辑 > 开始听写」菜单项 | **有效**，首次检出 +0.04 s |

也就是说：系统听写服务本身可用、音频与上屏链路都正常，被拒绝的只是「合成 Fn 作为触发源」。这与发送次数、间隔、事件投递层级和事件源都无关。

## 二、系统听写的触发机制

系统听写的快捷键菜单共 7 项：**按下 🌐**、连按两下 Control、连按两下 🌐、连按两下右 Command、连按两下左 Command、连按两下任一 Command、自定义…。这些选项落在两处配置，不是一处：

| 界面选项 | 配置位置 |
| --- | --- |
| 按下 🌐 | `com.apple.HIToolbox` 的 `AppleFnUsageType = 3`（Fn 键用途 = 开始听写） |
| 连按两下某修饰键 | `com.apple.symbolichotkeys` 的 `AppleSymbolicHotKeys` 第 `164` 项，`type = modifier` + 修饰位 |
| 自定义… | 同一项，`type = standard` + 键码与修饰位 |

读取方式（均不需要额外权限，App 无沙盒、只有 `audio-input` entitlement）：

- `CFPreferencesCopyAppValue("AppleSymbolicHotKeys", "com.apple.symbolichotkeys")` 可以一次读到全部符号热键（本机 27 条），含 164 项。
- `CFPreferencesCopyAppValue("AppleFnUsageType", "com.apple.HIToolbox")` 读 Fn 键用途。
- **`CopySymbolicHotKeys` 读不到听写**：本机返回 234 条里没有任何带 Fn 标志的条目，且数组下标与 symbolic ID 不对应（下标 164 是另一个 Shift+↑ 功能）。实现时不要走这条路。
- **`enabled = 1` 不代表该项被选中**：本机 164 项一直是 `enabled = 1`、`type = modifier`、`param0 = 0x800000`，而界面实际勾选的是「按下 🌐」。判断当前生效方式必须同时读 `AppleFnUsageType`，只看 164 会误判。

## 三、判定方法

听写是否真的在收音，用两个互相独立的信号判定，任一为真即视为已启动：

1. **窗口特征**：菜单栏出现 2 个 `Window Server / StatusIndicator`（28×28，右上角），且前台 App 名下出现一个 `layer = 3`、约 84×77 的浮窗（麦克风 HUD）。基线状态下两者均为 0。
2. **菜单项标题**：前台 App 的「编辑」菜单在「开始听写」与「停止听写」之间切换。

对照组证明该判定有效：用辅助功能对「编辑 > 开始听写」执行 `AXPress`，浮窗在 0.04 s 内出现；再点一次，菜单变为「停止听写」后浮窗消失。

## 四、另一个独立发现：只改偏好不足以启用听写

把 `com.apple.assistant.support` 的 `Dictation Enabled` 写成 `1` 之后，系统仍会弹出「你要启用"听写"吗？」确认框，必须由真人在对话框里点「好」，听写才真正开始工作（此前菜单项带省略号且点击无效）。

这意味着**应用无法替用户完成听写的启用**，只能引导用户自行开启；任何「检测到未开启就代为打开」的实现都不成立。

## 五、对「支持系统听写」方案的影响

- 「读取用户配置的听写快捷键，再按原样重放」这一方案在本机配置下不成立：用户的配置就是「按下 🌐」，而这个键恰恰是注入不进去的那一个。
- 唯一被验证可用的程序化驱动是点击「编辑 > 开始听写」菜单项。它依赖前台 App 暴露该菜单（系统 App 有，多数 Chromium/Electron 应用没有），并且需要向任意 App 的菜单栏注入点击，覆盖面和可靠性都不满足「任意输入框都能用」。
- 因此该路线若保留，只能退化为「提示用户自己按 Fn 说话」，产品价值有限，且与语音键本身冲突（FN 已被第三方输入法语音占用）。
- [PR #326](https://github.com/HD838A/remote-mic-app/pull/326) 用的是另一条分支：要求用户在系统设置里把听写快捷键改为「连按两下 Control」，再由遥控器发送两次 Control。本次**没有**验证 Control 路径（本机未配置该快捷键，临时改动用户配置超出本次范围），所以不能用本记录的 Fn 结论直接推断它可行或不可行；它需要按第三节的同一套判定方法单独复验。

## 六、未覆盖边界

- 连按两下 Control、连按两下 Command、自定义组合键是否接受合成事件（同一台机器未逐一验证）。
- 真实键盘按 Fn 的行为（本次由菜单对照组替代，未使用实体键盘）。
- 听写的麦克风选择项与语言项的配置位置：`com.apple.assistant.support`、听写容器目录和 `/Library/Preferences` 均未找到可读键，因此无法从代码判断用户是否已把听写麦克风指向虚拟声卡 `SayAll`。
- 听写开启后的首字延迟、定稿延迟、静音自动结束和「用户中途点完成」导致的状态错位，本次未测量；这些属于另一次评估的范围。

## 七、复现步骤

1. 在系统设置中开启听写并完成首次确认，确认「编辑 > 开始听写」可以正常启动。
2. 用一个空白文本窗口作为目标，记录监控前的窗口基线（菜单栏指示器数量应为 0）。
3. 通过 `CGEventPost` 发送一次 Fn（keycode 63、`flags = maskSecondaryFn`），在随后 3 秒内每 150 ms 采样第三节的两个信号。
4. 改为连续发送两次 Fn（间隔 80 ms）重复第 3 步；再分别改用 `cgSessionEventTap` 与 `combinedSessionState` 重复。
5. 三种注入方式都不产生信号，而辅助功能点击菜单项立即产生信号，即复现本记录结论。

用于验证的临时工具只保留在仓库外的工作目录，未进入版本控制。
