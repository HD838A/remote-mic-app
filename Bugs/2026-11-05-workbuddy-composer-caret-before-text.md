# 聚焦 WorkBuddy 后光标落在文字之前

- 时间：2026-11-05
- 状态：候选修复已提交（第五版：记忆/恢复语义），实机待验收
- 影响范围：macOS 预置 App 的“打开 / 聚焦输入框”（WorkBuddy、Codex、Claude）以及“记录目标输入框”的自定义 App；Windows 版本无此现象
- 功能点：`KeyboardInjector` 的 Accessibility 聚焦链路、`ComposerCaretTracker`
- 简单描述：用遥控器打开或聚焦 WorkBuddy 后，如果输入区此前没有焦点，插入点停在已有文字的最前面。用户随后把需求细化为“恢复到之前的状态”：手动移动过的光标要回到原位；无记忆或丢失聚焦时默认到文字最后；空输入框不得丢失聚焦。
- 原始记录：用户反馈「如果之前聚焦在输入框，那么打开 wb 时，聚焦位置在文字最后；如果之前没聚焦在输入框，那么打开 wb 时，聚焦位置在文字之前；Windows 版本是没有这个问题的」，后续依次补充「光标有从开头变到结尾的过程」「没有文字的时候会先聚焦然后丢失聚焦」「我需要直接到最后」「恢复到之前的状态，比如用户手动将光标移动了，下次进来应该还在原来的位置上」

## 复现

1. 在 WorkBuddy 对话输入区留下脱敏测试文字，不发送。
2. 把焦点移到侧边栏或其他 App，让输入区失去焦点。
3. 触发已映射的“打开 WorkBuddy”按键。
4. 观察插入点：落在文字最前面，接着说话会把首字插到整段内容之前。
5. 保持输入区聚焦再触发同一动作，插入点则停在用户上次离开的位置，通常是末尾。

Windows 版本在两种入口下都落到末尾，因此用户看到的是平台之间的行为差异。

## 日志与根因

### 根因一：只设焦点不设插入点

聚焦只做了三步：判断是否已聚焦、设 `AXFocused`、设应用级 `AXFocusedUIElement`，失败再 `AXPress`。整条链路没有写入选区，所以落点完全由目标 App 自己决定。Chromium/Electron 宿主在没有历史选区时把插入点放在偏移 0，于是出现“文字之前”。

在隔离的 Chromium 156 实例上验证：只设 `AXFocused` 后选区仍为 `(0,0)`；聚焦态写 `AXSelectedTextRange` 到 `(12,0)` 后输入落在末尾；聚焦后发送 Cmd+Down，选区从 `(0,0)` 读回 `(11,0)`。

### 根因二：字符数上报不可信，按字符数写选区在空输入框越界

WorkBuddy 对话输入区的 `AXNumberOfCharacters` 恒报 27，而真实内容长度为 0（越界写入 + 读回钳制值探测确认），AX 选区状态与编辑器真实状态脱节。按字符数写选区在空输入框都是越界写，与用户“空输入框先聚焦然后丢失聚焦”的反馈对应；写选区后的立即读回还常拿到旧值，无法作为可靠确认。

### 根因三：确认读窗口内宿主先画出偏移 0 的光标

聚焦设置之后、末尾键发送之前有一次聚焦确认读（几十毫秒），宿主在这段窗口里已经把偏移 0 的光标画出来，形成“先在文字之前、再闪到末尾”的可见过程。越界钳制预置不可行：Chromium 对越界选区写入直接重置为 0，不会钳到末尾。

### 现象补充：已在前台时按键导致焦点闪断

焦点观察器（120ms 采样）显示：目标 App 已在前台、输入框已有焦点时按键，焦点先变 `nil` 约 1.5–2 秒再回到输入框。原因是 `openApplication(activates: true)` 对已在前台的实例仍执行一遍激活仪式，窗口经历 resign/become key，页面 DOM 焦点被清空后由系统恢复；与文字多少无关，空输入框时最容易被察觉。无线麦日志中按键均以 `succeeded` 结束，说明这不是聚焦链路失败，而是激活仪式本身。

## 修复（最终方案：记忆 / 恢复）

- 新增 `ComposerCaretTracker`（`ComposerCaretStore` + `ComposerCaretObserver`）：按目标 App Bundle ID 记忆输入框最近的光标偏移，只记偏移、从不读取或保存输入内容。聚焦期间用 `AXObserver` 订阅 `AXSelectedTextRangeChanged` 通知，用户手动移动光标也会被记录；通知回调挂在 `EventTapRunLoop` 专用线程。
- 已聚焦入口：读取当前偏移记入记忆并保持跟踪，**不移动光标**——当前状态就是用户要的状态。
- 未聚焦入口：聚焦设置**之前**先预置记忆偏移——宿主把它缓存为该输入框的选区，聚焦在同一帧直接恢复到这个位置，不会先画出偏移 0 的光标；聚焦确认后幂等重写一次（AXPress 兜底路径则抵消按压落点）。宿主对越界偏移自行钳制，内容变短后等价于“回到文字最后”。**没有记忆偏移时才发送末尾键 Cmd+Down**（含 Command 按下/释放的完整和弦，保证系统修饰键状态归零），并在确认后补发一次兜底。
- 已在前台时 `open` 跳过重复激活（`reason=already_frontmost`），避免激活仪式清空页面焦点 1.5–2 秒。
- cmux 终端聚焦显式关闭光标处理（`restoresComposerCaret: false`）。
- 日志只记录 `APP FOCUS caret bundle=<bundle> role=<role> result=<token>`（`remembered` / `restored` / `end_key_sent` / `remember_failed` / `restore_failed` / observer 的 `observing` 等）与 `APP ACTION skipped ... reason=already_frontmost`，不含文字、长度、字符数或选区内容。

### 方案演进记录

1. 第一版：聚焦后按 `AXNumberOfCharacters` 写 `AXSelectedTextRange`——消除落点差异，但光标先出现在开头再跳到末尾，有可见跳变。
2. 第二版：聚焦前预置选区——消除跳变，但 WorkBuddy 字符数上报不可信，空输入框越界写入伴随“先聚焦再丢失聚焦”的反馈。
3. 第三版：放弃选区写入，聚焦确认后发送标准末尾键——仍有“先 0 再闪到末尾”（确认读窗口内宿主先画出偏移 0）。
4. 第四版：末尾键提前到聚焦设置后立即发送 + 确认后兜底补发——闪动消除；同时确认越界钳制预置不可行（Chromium 直接重置为 0）。
5. 第五版：应用户新需求由“一律末尾”改为“记忆 / 恢复”——AXObserver 跟踪选区偏移，未聚焦入口优先写回记忆偏移，无记忆才发末尾键；已聚焦入口只记忆不移动。
6. 第六版（当前）：恢复写回提前到聚焦设置**之前**预置——记忆偏移来自真实选区捕获，预置在实测宿主上可靠生效，聚焦同帧直接恢复，消除恢复路径的闪动；越界值仍由宿主钳制。

## 验证

- 自动化：`composerCaretStoreRemembersOffsetsPerBundle` 覆盖记忆写入、覆盖与非法偏移拒绝；`composerCaretUsesTheStandardEndOfDocumentKey` 锚定末尾键值；`alreadyFrontmost*` 两个测试覆盖已在前台跳过激活。
- 机制实测：Cmd+Down 在隔离 Chromium 把选区从 `(0,0)` 移到 `(11,0)`；聚焦态越界写在空编辑器不丢焦点（`focused=true` 保持）；WorkBuddy 字符数与真实长度脱节用越界写入钳制法确认。
- 待验收：WorkBuddy、Codex、Claude 与自定义 App 的实机“移动光标 → 切走 → 回来恢复原位”、越界钳制、空输入框、已在前台不闪断、语音首字和实体遥控器，按 `Testing/CustomApplicationFocus.md` 的用例 0E 执行。

## 兼容与剩余边界

- 没有 UI、配置结构或权限变更；不读取任何输入内容，只使用公开可访问性接口的偏移与计数；AXObserver 通知回调只读选区偏移。
- 记忆键是目标 App 的 Bundle ID：同一 App 多个窗口/输入框共享一份记忆；无线麦重启后记忆清空，按默认末尾处理。
- 恢复写入依赖宿主对越界偏移的钳制；末尾键依赖宿主对 macOS 标准键的默认处理。两者在实测的三大 Chromium 宿主上成立，个别宿主异常时需按宿主补充豁免。
- 行为变化：已聚焦入口不再强制把光标移到末尾（保持用户位置）；这是用户确认的需求变更，替代此前的“一律末尾”。
