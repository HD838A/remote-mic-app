# Onboarding 语音测试偶发没有写入文字

- 时间：2026-08-18
- 状态：候选修复完成，自动化与生产视图截图已验证；真实豆包与实体遥控器仍待用户验收
- 影响范围：macOS Onboarding 语音测试页
- 现场版本：无线麦SayAll.app `1.8.25 (119)`、macOS 26、arm64、豆包输入法、实体遥控器
- 简单描述：豆包输入法显示输入电平，无线麦也收到完整语音样本，但松开后输入框偶发没有文字；留在同一页面再次操作又可以恢复。输入框的光标与占位符起点同时存在视觉错位。

## 复现与边界

现场触发条件：选择豆包输入法并完成实体遥控器、权限和音频设置，进入语音测试页后直接按住遥控器语音键说话并松开。

错误行为：豆包有输入电平，页面显示语音开始、样本到达和会话结束，但最终没有文字，诊断停在 `voice.no_transcript`；同一页面稍后重试可能恢复。截图中输入框已有蓝色焦点边框，但光标位于占位符左上方，二者的字体和内容起点不一致。

正常边界：进入页面、从其他 App 返回以及点击重新测试后，输入框都应自动成为系统实际文字写入目标；用户不需要额外点击。占位符、光标与正文应从同一位置开始。

代理环境无法安装并驱动用户的真实豆包输入法与实体遥控器，因此没有稳定复现文字丢失；本次以用户现场日志、页面截图和“同页再次操作恢复”作为竞态证据，最终结论仍需现场复验。

## 日志结论

用户现场诊断显示：

- 已成功选择豆包输入源并应用 Fn 映射；
- 控制方式已连接，语音键按下与松开均被观察到；
- `voice_started=true`、`voice_samples_received=true`、`voice_ended=true`；
- 四次语音均走虚拟音频输出，入队失败为零；
- 会话结束后只剩极少量短缓冲并迅速排空；
- 最终唯一未通过条件是 `transcription_appeared=false` / `voice.no_transcript`。

这些证据排除了蓝牙未连接、遥控器没有发出语音会话、PCM 没有到达、音频输出未就绪和明显尾部未排空。豆包有实时电平也证明虚拟麦克风链路已工作，但不能证明 macOS 当时把识别结果提交到了正确的文本控件。

## 根因假设

`prepareForStep(.voiceTest)` 在父视图切换时只通过一次主队列异步修改 SwiftUI `FocusState`。该请求可能早于 `TextEditor` 的底层 `NSTextView` 真正挂载；蓝色边框反映 SwiftUI 焦点状态，却不能单独证明它已经是输入法提交文字时的 first responder。

“同一页面稍后再次操作可以恢复”与挂载时序竞态一致。当前证据不足以宣称第三方输入法自身没有其他偶发行为，因此把该结论记录为高置信度根因假设，而非已通过真机稳定复现的唯一根因。

## 修复

- `TextEditor` 真正出现后再次请求焦点。
- 进入语音测试页、App 从后台返回以及点击重新测试时，先清除旧焦点状态，再在下一次主队列调度重新聚焦。
- 获得焦点时继续重新选择用户在 Onboarding 中保存的豆包或微信输入法。
- 记录不含文字内容的焦点布尔日志，便于区分“音频正常但输入目标没有恢复”。
- 占位符改用与正文相同的 15pt 字号，并校准内边距，使占位符、光标和正文起点一致。
- 移除“只要 transcript 已非空就把焦点状态改为 true”的反向逻辑，避免把已有文字误当成实际焦点证据。

## 验证

- 定向源码契约测试覆盖输入框出现、回到前台、重试时的重新聚焦，以及占位符字号与内边距。
- 生产 `OnboardingView` 已生成实体遥控器路径的浅色和深色页面，语音测试页无滚动、无裁切，占位符在两种外观下位置一致。
- `swift test --filter OnboardingFlowTests`：22 项通过。
- `swift test`：234 项、20 个 suite 全部通过。
- `scripts/test.sh`：42 项项目自检通过。
- `swift build`、`git diff --check` 与中英文 strings `plutil -lint` 通过。

## 验证边界

离屏截图不能显示真实键盘 first responder，也不能证明豆包最终提交文字；单元测试和构建同样不能替代真实豆包、微信输入法、Typeless、RC001 / RC003、前后台切换和文字上屏验收。用户需要用原始失败路径确认首次进入、返回 App 和点击重试后三种情况都无需手动点击输入框。
