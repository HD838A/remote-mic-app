# 语音记录在快速发送或连续语音时丢失

- 时间：2026-08-17
- 状态：已修复并通过真实 RC003、千问与微信验收
- 影响范围：macOS 本地语音记录；目标输入框在候选稳定前被发送清空、失去焦点或紧接下一次语音
- 功能点：本地语音转写记录
- 简单描述：目标 App 已经出现语音文字，但用户很快发送或开始下一段语音时，本次历史记录可能没有保存。
- 原始记录：用户现场操作、`~/Library/Logs/RemoteMic/runtime.log`、本地 `Transcripts/v1` 文件和根目录 `DEBUG.md`

## 复现条件与错误边界

1. 开启“保存语音记录”。
2. 在 Codex 可编辑输入框完成一段语音。
3. 文字出现后约 1 秒内按 Return 发送，或立即开始下一段语音。

错误行为：文字已经进入目标 App，但语音记录页没有对应条目。

正常边界：TextEdit 中等待文字稳定后可以保存；同一 Codex 输入框中让文字保留足够时间也能连续保存，证明权限、Codex Accessibility 和归档存储并非持续不可用。

## 日志与文件证据

- Codex 会话 23 于 `18:30:30Z` 停止，`18:30:31Z` 收到 Return，没有对应 JSON 记录。
- Codex 会话 24 于 `18:31:15Z` 停止，下一会话于 `18:31:16Z` 开始，没有对应记录。
- Codex 会话 25、27、28 的候选文字保留更久，分别成功保存三条记录。
- 失败期间没有 `TRANSCRIPT ARCHIVE update_failed`，说明未进入归档回调，不是磁盘写入或统计页刷新失败。
- 最初会话 19、20 也没有落盘，但旧版本没有候选阶段诊断日志，无法逐毫秒确认其具体取消点。

## 假设与实验

根目录 `DEBUG.md` 记录了四个候选原因。最小实验在协调器已经观察到合法文字后、稳定满 0.9 秒前把输入框恢复为空值；旧实现的 `harness.captures` 稳定为空，复现现场错误并确认候选被取消逻辑丢弃。

## 根因

`TranscriptCaptureCoordinator` 把稳定 0.9 秒作为唯一提交条件，但输入框清空、焦点变化和下一会话开始都会无条件取消当前会话；已观察到且通过原始光标连续差异校验的候选因此来不及提交。

## 修复

- 保留最后一个通过安全目标、同一 App、同一输入元素和原选区连续差异校验的候选。
- 输入框快速清空、焦点离开或下一次语音开始时，先提交已存在的合法候选；没有候选时仍取消。
- 周围文字发生无关编辑、敏感目标、功能关闭和语音过程中目标变化继续拒绝，不扩大采集范围。
- 新增不含正文的 `TRANSCRIPT CAPTURE` 诊断日志，只记录结果原因、Bundle ID 和字符数。

## 验证

- 修复前最小实验：失败，候选在输入框清空后丢失。
- `swift test`：236 项、22 个 Suite 全部通过，包含快速发送、连续语音、恢复非空原稿不误存和独立侧边栏页面回归。
- `plutil -lint Resources/Info.plist Resources/en.lproj/Localizable.strings Resources/zh-Hans.lproj/Localizable.strings`：通过。
- `git diff --check`：通过。
- Release App：`1.8.5 (68)` 构建成功，`codesign --verify --deep --strict` 通过，主程序为 `arm64`，且 `SayAllAIIncluded=false`，证明无私有 AI 包也可构建。
- 页面实测：独立“语音记录”入口位于“统计”下方，TextEdit 与 ChatGPT 显示真实 App 图标，宽布局无裁切；窗口受既有最小尺寸约束，申请 `800 × 650` 时实际保持约 `980 × 764`。

## 验证边界

## 2026-08-25 千问确认时序追加调查

### 观察

- 本地“记录回眸”开关已开启，归档目录可正常写入，页面也能显示成功保存的记录。
- 同一台 RC003 在千问模式下多次完成语音并自动确认，但日志反复出现 `discontinuous_text_change`、`snapshot_unavailable_after_finish` 和 `timeout`；没有归档读写失败。
- 10:48 的一次会话成功保存 69 个字符，实时窗口随即显示 1 条记录，排除页面、开关和磁盘存储持续失效。

### 根因

千问模式在音频排空后立即释放右 Command 并发送 F20 确认。回眸此时仍在等待输入框文字稳定；确认动作会清空输入框或改变编辑状态，因此多数会话在取到最终候选前被取消。

第一次候选修复真机验收时，连续三次语音只新增一条：两次为 `discontinuous_text_change`，一次保存 6 个字符。进一步的最小测试证明 `finishSession` 会立即轮询，并在 F20 前置钩子执行前取消；同时千问连续输入时 macOS 偶尔仍上报旧光标位置，即使原草稿完整保留且只在其他位置新增了语音文字。

第二次真机验收中，四个有效长按会话保存三条，首个会话仍为 `discontinuous_text_change`；后续三条分别保存 19、15、23 个字符。说明剩余边界不是页面、存储、F20 或纯新增，而是千问把选中文字替换为最终识别结果时，系统仍上报旧选区。

### 修复

- 蓝牙会话先结束回眸采集时钟，再启动千问的音频排空与确认流程。
- 在 F20 确认前，同步提交已经满足同一输入框、同一 App、原选区连续变化与非敏感目标校验的候选。
- 千问会话的首次结束轮询允许忽略过期光标，但只接受“原文字完整保留、单点纯新增”的变化；替换或删除原文仍拒绝。
- 对同一安全输入框里的替换，不再立即保存；必须保持 0.9 秒稳定且光标位于替换后文字末尾，才把新文字作为本次转写保存。普通语音模式仍拒绝旧选区之外的替换。
- 没有合法候选时继续沿用原取消逻辑，不扩大采集范围。

### 验证

- 新增“旧光标但原文完整保留并纯新增”“替换原文仍拒绝”“确认前输入框即将清空”的协调器回归，以及“释放 Command → 保存候选 → F20 确认”的顺序回归。
- 定向回归：19 项、3 个 Suite 全部通过，包含 TV 的 ISO/ANSI 原生键码抑制。
- `swift test`：409 项、37 个 Suite 全部通过。
- 第二次追加后的定向回归：21 项、3 个 Suite 全部通过；完整 `swift test`：411 项、37 个 Suite 全部通过。
- 真实 RC003 / 千问仍需在替换本地 App 后连续说 3 次，核对每次日志均为 `saved reason=qianwen_confirm` 或 `saved reason=stable`，并确认回眸新增 3 条。

## 2026-08-25 微信输入框不可读边界

### 观察

- 同一安装包中，Codex、Ego Lite 和 Telegram 均能取得输入框快照并保存回眸记录。
- 微信四个有效长按会话全部先等待 1.25 秒，随后以 `initial_focus_unavailable` 跳过；语音输入和 F20 确认本身正常。
- 微信聊天主窗口只向 Accessibility 暴露窗口级结构，不暴露聊天输入框的文字、选区或可编辑元素。既有短按定位依赖窗口相对点击，因此“能聚焦、能说话”不等于“能读取文字”。
- 千问输入法本地 `VoiceUsage/voice_usage.json` 含完整语音历史，但 payload 标记为 `unet_internal_wsg_base64`；千问二进制明确限制解密能力只在其输入法服务进程内，SayAll 没有公开读取接口。

### 结论与边界

这不是现有回眸状态机可继续放宽的漏记路径。微信需要新的文字来源：要么使用会暂时改动通用剪贴板和选区的微信专用“全选复制”回退，要么在 SayAll 内新增独立语音识别。前者会影响用户编辑状态，后者需要新的识别模型或系统语音权限；未获得产品取舍前均不自动实施，也不逆向千问私有加密协议。

### 社区反例与环境差异

- 社区截图显示另一台机器的回眸已有微信 29 条、企业微信 42 条，证明“所有微信版本都无法记录”的结论不成立。
- 本机为微信 `4.1.12 (269365)`、macOS `15.6.1`。只读遍历主进程 Accessibility 树得到 250 个节点、可编辑节点为 0，且 `AXEnhancedUserInterface=true`，不是 SayAll 未尝试增强辅助界面。
- 社区截图中的 SayAll 有“组合动作”。官方 `1.9.10 (136)` ZIP 实测包含 `SayAllAIIncluded=true` 与 `SayAllMacroPlatformIncluded=true`；本地源码构建均为 false，因为当前 GitHub 身份无权读取两个私有仓库。
- 公开回眸实现与回归明确要求 `TranscriptCaptureCoordinator` 不依赖 `PrivateFeatureIntegration` 或 API；官方与本地二进制也包含同一套 `TRANSCRIPT CAPTURE` 诊断。因此私有组件能解释界面差异，但没有证据证明它是微信记录来源。
- 当前最强假设是社区机器使用仍暴露可编辑输入框的微信旧版本、不同安装渠道或界面灰度。需要对方提供微信“关于”版本、安装来源、macOS 版本和 SayAll 版本，才能继续区分版本回归与灰度差异；仅凭回眸截图不能确定。
- 本机微信没有 Mac App Store receipt，属于官网或其他渠道安装的 `4.1.12`；Apple 当前 Mac App Store 页面仍列 `4.1.11`。因此“官网 4.1.12 与 App Store 4.1.11 的 Accessibility 差异”是可验证的首要分支，但在拿到社区用户版本前仍只是强假设，不建议直接降级微信。

### 千问本地历史 Helper 修复与真机验收

- 新增独立 `QianwenHistoryReader`，只在“千问模式＋微信＋已开启回眸”时使用；普通 App 继续走 Accessibility 差异捕获。
- Helper 由 `sandbox-exec` 禁止网络和文件写入，只读取千问本地加密语音历史，使用千问已安装的本地运行库解密，并按当前语音时间窗返回一条最终文字；正文只通过父子进程管道传给 SayAll，不写日志。
- Helper 单独签名并进入 App 验证清单；千问版本、运行库、格式或字段不匹配时失败关闭，不影响语音、按键和其他 App 回眸。
- 真实 RC003 / 微信验收：`ATVV STREAM accepted → AUDIO PLAYBACK drained → QIANWEN CONFIRM F20 → QIANWEN HISTORY saved`；最终保存 10 个字符，回眸落盘出现微信第 1 条记录。用户确认微信文字可记录，手机不再出现“断开 Mac”提示。
