# 语音记录在快速发送或连续语音时丢失

- 时间：2026-08-17
- 状态：修复完成，完整自动化与 Release App 构建通过；真实 RC001/Codex 快速发送仍待新测试包复验
- 影响范围：macOS 本地语音记录；目标输入框在候选稳定前被发送清空、失去焦点或紧接下一次语音
- 功能点：本地语音转写记录
- 简单描述：目标 App 已经出现语音文字，但用户很快发送或开始下一段语音时，本次历史记录可能没有保存。
- 原始记录：用户现场操作、`~/Library/Logs/RemoteMic/runtime.log`、本地 `Transcripts/v1` 文件和根目录 `DEBUG.md`

## 复现条件与错误边界

1. 开启“保存语音记录”。
2. 在 Codex 可编辑输入框完成一段语音。
3. 文字出现后约 1 秒内按 Return 发送，或立即开始下一段语音。

错误行为：文字已经进入目标 App，但语音记录页没有对应条目。

正常边界：TextEdit 中等待文字稳定后可以保存；同一 Codex 输入框中让文字保留足够时间也能连续保存，证明权限、Codex Accessibility 和归档存储并非持续不可用。

## 日志与文件证据

- Codex 会话 23 于 `18:30:30Z` 停止，`18:30:31Z` 收到 Return，没有对应 JSON 记录。
- Codex 会话 24 于 `18:31:15Z` 停止，下一会话于 `18:31:16Z` 开始，没有对应记录。
- Codex 会话 25、27、28 的候选文字保留更久，分别成功保存三条记录。
- 失败期间没有 `TRANSCRIPT ARCHIVE update_failed`，说明未进入归档回调，不是磁盘写入或统计页刷新失败。
- 最初会话 19、20 也没有落盘，但旧版本没有候选阶段诊断日志，无法逐毫秒确认其具体取消点。

## 假设与实验

根目录 `DEBUG.md` 记录了四个候选原因。最小实验在协调器已经观察到合法文字后、稳定满 0.9 秒前把输入框恢复为空值；旧实现的 `harness.captures` 稳定为空，复现现场错误并确认候选被取消逻辑丢弃。

## 根因

`TranscriptCaptureCoordinator` 把稳定 0.9 秒作为唯一提交条件，但输入框清空、焦点变化和下一会话开始都会无条件取消当前会话；已观察到且通过原始光标连续差异校验的候选因此来不及提交。

## 修复

- 保留最后一个通过安全目标、同一 App、同一输入元素和原选区连续差异校验的候选。
- 输入框快速清空、焦点离开或下一次语音开始时，先提交已存在的合法候选；没有候选时仍取消。
- 周围文字发生无关编辑、敏感目标、功能关闭和语音过程中目标变化继续拒绝，不扩大采集范围。
- 新增不含正文的 `TRANSCRIPT CAPTURE` 诊断日志，只记录结果原因、Bundle ID 和字符数。
