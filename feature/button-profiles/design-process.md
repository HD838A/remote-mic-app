# 复杂功能设计流程

这份经验来自“组合动作”和“键位方案”的多轮设计与实测。目标不是把所有能力都展示出来，而是让第一次使用的人不需要理解实现，也能知道自己现在要做什么、下一步在哪里、保存后会发生什么。

## 1. 先写清用户最终要完成的事

在画页面或写代码前，先用一句普通话描述结果。例如：

> 为遥控器保存一套按键设置，并决定自己切换，还是在打开某个 App 时自动使用。

如果这句话必须依赖 Bundle ID、绑定、触发器、规则或数据格式才能解释，说明产品模型还没有翻译成用户模型。

## 2. 先拆对象，再排页面

复杂功能常同时包含“可复用内容”和“在哪里使用”。两者必须分开：

- “组合动作”负责定义按下后连续做什么。
- “键位方案”负责一整套遥控器按键如何设置。
- 具体遥控器按键只引用已经保存的内容，不在每个按键下面重复建设完整编辑器。

每个重要对象应有独立入口、列表、查看状态和编辑流程。不要因为代码可以复用，就把不同心智模型塞进同一个页面。

## 3. 用步骤引导完成，而不是一次铺开所有设置

创建流程先找出真正存在先后关系的任务，再按用户决策顺序排列：

1. 起一个容易识别的名字。
2. 选择什么时候使用。
3. 逐个设置按键。
4. 检查并保存。

每一步只展示完成当前任务所需的内容。用户可以返回上一步，草稿不能丢失；保存前不能悄悄改变正在运行的设置；最后一次提交要么全部成功，要么全部保持原样。

## 4. 页面铺平不等于把全部功能同时展开

“少弹窗、少下拉”解决的是上下文丢失，不代表所有选项都要永久展开。

- 当前步骤需要的内容在页面内完成。
- 大量选项按“基础按键、系统与媒体、App、组合动作”等用户能理解的类别分区。
- 次要内容可以折叠，但不能把不同类别混进一个很长的下拉列表。
- 系统文件选择和必要权限仍可使用系统弹窗。

判断标准是：用户是否一直知道自己在设置哪个对象，以及完成后会影响什么。

## 5. 空状态必须直接告诉用户下一步

当列表为空时，用户没有可探索的内容。页面应同时提供：

- 一句说明这里能做什么。
- 一个唯一、醒目、带动词的主按钮。
- 点击后直接进入第一步，不再要求用户寻找侧栏或工具栏入口。

如果创建是当前唯一任务，主按钮应位于内容区视觉中心，并使用大号、主色和清楚的图标。说明文字不能代替操作入口。

## 6. 把实现语言翻译成任务语言

内部技术名可以保留在代码、日志和技术文档，但不能直接出现在普通页面。

| 实现语言 | 用户语言 |
| --- | --- |
| Bundle ID | App 名称和图标 |
| 前台 App | 正在使用的 App |
| 触发方式 | 按法 |
| 当前动作 | 按下后会 |
| 取消绑定 | 恢复原来的设置 |
| 普通按键映射 | “按键”页面中的设置 |
| 自动切换规则 | 选择自动使用的 App |
| 本地快照 | 不展示；只在需要恢复时说明可以找回 |
| 循环引用 | 组合动作不能直接或间接执行自己 |

每一条文案都要回答用户的任务问题。不会改变用户决定或操作的信息，应从普通页面移除。

## 7. 把“不会丢”设计成产品行为

复杂编辑最容易破坏信任。必须明确：

- 切换步骤不丢草稿。
- 切换编辑对象前自动保存，或明确阻止切换并说明原因。
- 不同类型的设置分别保留；暂时切换到其他类型后，再切回来仍可继续使用原内容。
- 支持撤销时，历史能力可以先隐藏在一个清楚的“撤销”按钮后面，不必一开始暴露完整版本系统。
- 导入导出必须覆盖用户能设置的全部内容，并对只存在于本机的 App、快捷指令或输入框记录给出普通提示。

## 8. 编辑页面不能意外执行旧设置

当用户在遥控器图片上选择按键时，按下实体按键的含义已经变成“选择要编辑的按键”。此时不应同时执行旧操作、打开其他 App 或发出错误音。离开编辑页面后，再恢复正常执行。

同一个输入在不同页面可能有不同含义，必须把页面状态、路由和执行边界一起设计，不能只完成视觉页面。

## 9. 验证完整流程，不只验证控件存在

自动化至少覆盖：

- 文案中不出现内部标识和禁止术语。
- 空状态存在大号主创建按钮。
- 步骤门禁、草稿保持、取消和统一保存。
- 不使用混合长下拉或连续弹窗。
- 最小窗口、中文最小 12pt 和中英文资源完整。

人工测试必须从第一次进入开始，完整走完“空状态 → 新建 → 每一步 → 保存 → 实体按键执行 → 编辑 → 取消/再次保存”。涉及真实遥控器、权限、第三方 App、锁屏和前后台的状态要拆开测试。构建成功或单元测试通过不能代替真实用户流程。

## 10. 小学生可用性检查

交付前，请让评审者不看需求文档，只看页面回答以下问题：

1. 这页是做什么的？
2. 我现在应该点哪里？
3. 每个选项会发生什么？
4. 我还差几步完成？
5. 保存前会不会改坏现在的设置？
6. 如果我选错了，能不能返回、取消或撤销？

任何一个问题需要开发人员解释，页面就还没有完成。先修改结构和文案，再考虑增加帮助说明。

## 交付清单

- 用户目标能用一句普通话说清。
- 不同对象有独立入口，不按代码结构混页。
- 创建流程按决策顺序分步。
- 空状态有唯一且醒目的主操作。
- 选项按用户类别分组，不用混合长下拉。
- 页面不显示内部标识和实现术语。
- 草稿、取消、保存和撤销行为明确且不丢内容。
- 编辑输入不会意外执行旧功能。
- 自动化、构建、代理实测和真实环境验收边界分别记录。
