# 遥控器连接生命周期与手动恢复方案

- 状态：设计评审中，未开发
- 日期：2026-11-15
- 范围：macOS 已登记遥控器档案、BLE 连接、共享发现、手动恢复、日志和后续页面入口
- 明确不包含：本方案的实现代码、页面代码、删除用户数据、改变选中遥控器的语音/按键语义

## 1. 问题

一只已登记但不再选中的旧 RC001 档案在 App 启动后持续重连。现场日志记录到 17 次 `BLE CONNECT TIMEOUT`、26 次 `BLE RECONNECT scheduled`，失败计数增长到 25；重试间隔从约 3 秒增长到 60 秒封顶后，约每 60 秒重复。同一时间选中的 RC003 保持 `BLE READY`，连接页一直显示 RC003 已连接。

旧档案不是空壳：它有型号、HID 指纹和六类按键映射，可能是曾经配对过的第二只真实遥控器。不能静默删除。

当前实现有三个独立问题叠加：

1. 每个带 Bluetooth identifier 的档案都会创建一个主动重连桥。
2. 主动重连桥对所有档案使用同一套无上限的 3–60 秒退避。
3. 连接页只显示已连接设备，未连接档案没有可见卡片，也没有独立的手动恢复入口。

## 2. 当前行为和历史原因

### 2.1 每个档案一个主动桥

`BridgeAppModel.startBluetoothConnections()` 遍历 `remoteDeviceProfiles`，为每个带 `bluetoothIdentifier` 的档案创建 `XiaomiBluetoothBridge`。旧档案的桥不知道用户是否还在使用它，只按自己的失败计数重连。

### 2.2 卡片只显示已连接设备

PR [#143](https://github.com/HD838A/remote-mic-app/pull/143) 在 2026-08-22 合入，把设置页设备选择器从“全部档案”改成“当前 `ready` 的档案”。原因见 [`Bugs/2026-08-21-settings-connected-remotes-only.md`](../../Bugs/2026-08-21-settings-connected-remotes-only.md)：多个历史断开档案挤压连接页和按键映射页。

副作用是旧档案断开后没有卡片，用户无法点击它重连。

### 2.3 已有发现桥

`BridgeAppModel.discoveryBluetoothBridge` 已经存在。它没有目标 identifier，负责扫描广播、查询系统已连接设备、连接新设备，并在成功后把桥交接给对应档案。当前它排除所有已创建主动桥的 identifier，因此不会发现旧档案。

### 2.4 历史修复边界

- PR [#530](https://github.com/HD838A/remote-mic-app/pull/530)：只在握手完成后持久化档案，见 [`Bugs/2026-09-05-ghost-remote-profile-from-unready-peripheral.md`](../../Bugs/2026-09-05-ghost-remote-profile-from-unready-peripheral.md)。该修复明确不处理已经存在的幽灵档案。
- PR [#632](https://github.com/HD838A/remote-mic-app/pull/632)：修复缓存直连失败后扫描永久停滞，增加 20 秒扫描窗口和既有退避，见 [`Bugs/2026-10-11-ble-scan-stall-after-cached-target-bypass.md`](../../Bugs/2026-10-11-ble-scan-stall-after-cached-target-bypass.md)。
- PR [#921](https://github.com/HD838A/remote-mic-app/pull/921)：唤醒后查询系统已连接候选，并保留缓存冷却探测，见 [`Bugs/2026-11-07-ble-wake-recovery-stall.md`](../../Bugs/2026-11-07-ble-wake-recovery-stall.md)。
- Issue [#441](https://github.com/HD838A/remote-mic-app/issues/441)：后台主动 BLE 扫描可能参与 DarkWake/亮屏循环。本方案不得增加空闲扫描占空比，必须继续遵守系统挂起和睡眠边界。
- Issue [#935](https://github.com/HD838A/remote-mic-app/issues/935)：真实 RC001 在语音中反复断连并出现连接/加密超时。共享发现和有限恢复必须覆盖这条现场风险。
- Issue [#356](https://github.com/HD838A/remote-mic-app/issues/356)、[#1041](https://github.com/HD838A/remote-mic-app/issues/1041)、[#631](https://github.com/HD838A/remote-mic-app/issues/631) 分别覆盖唤醒恢复、采纳但未真正发起连接、首次重连失败后扫描停滞。

### 2.5 已否决的 30 分钟退避试验

2026-11-15 评估过一个最小补丁：非选中档案前两次 3、6 秒，之后按 2、5、10、30 分钟退避。它能降低连接频率，但第二只真实遥控器重新开机后可能等待数分钟到 30 分钟，且连接页只显示已连接设备，用户看不到卡片，无法主动恢复。该试验不满足“自动恢复不能延迟太多，或至少要有手动入口”的原则，因此不作为本方案，也不纳入本 PR。

## 3. 设计原则

1. 不无限重试。没有证据表明设备会回来时，不能永久按固定间隔发起主动连接。
2. 不能日志爆炸。发现、失败和恢复只记录状态转换和有界汇总，不按每台广播设备刷屏。
3. 自动恢复优先。设备实际出现时，应在发现延迟内恢复，不能依赖 30 分钟退避。
4. 手动入口必须存在。自动恢复失败时，用户能找到并触发恢复，不依赖未连接卡片。
5. 不静默删除档案或映射。删除只能由用户明确确认，并保留映射导出能力。
6. 选中遥控器的语音和按键快速路径不能被旧档案阻塞。
7. 页面修改必须先出 HTML 设计稿并取得用户确认，确认前不写 SwiftUI。

## 4. 目标状态模型

每个已登记档案拥有一个连接状态，状态只描述当前链路，不表示档案是否有效：

| 状态 | 含义 | 主动连接 | UI |
| --- | --- | --- | --- |
| `connected` | 已 `ready` | 否，保持连接 | 现有已连接卡片 |
| `recovering` | 选中档案刚断开，处于有限主动恢复窗口 | 是，有限次数 | 可显示“正在重连” |
| `waiting` | 等待设备出现 | 否，只被动发现 | 可在“其他已登记遥控器”中显示 |
| `manualOnly` | 用户停止自动连接 | 否，仅手动 | 可选管理入口 |
| `forgot` | 用户确认忘记 | 否 | 档案和映射按确认结果处理 |

`manualOnly` 和 `forgot` 需要页面入口，属于后续页面阶段，不在本设计评审通过后立即开发。第一阶段可以只实现前三种状态，用现有“立即重新连接”按钮作为手动入口。

## 5. 推荐方案

### 5.1 选中档案：有限主动恢复

选中档案允许主动重连，但必须有边界：

- 断开后依次尝试 3、6、12、24、48、60 秒；
- 最多 6 次，约 2.5 分钟；
- 仍未连接则进入 `waiting`，停止主动连接；
- 语音键按下、用户点击“立即重新连接”、App 回到前台，可以开启新的有限恢复窗口；
- 同一档案的重复触发要有最小间隔，避免用户连续操作造成新的连接风暴。

这样处理的是“刚断开的选中遥控器需要快速回来”，而不是“设备永远不回来也每分钟重试”。

### 5.2 非选中档案：共享发现按需接入

不再为非选中档案创建主动重连桥。复用现有发现桥：

- 只保留一个发现桥扫描和查询系统已连接设备；
- 发现桥可以看见已登记但处于 `waiting` 的档案；
- 看到设备后连接，成功后交接给原档案；
- 复用原 profile、HID 指纹和全部映射，不新增重复档案；
- 设备关机或离开范围时不发起盲连，只保留被动发现；
- 非选中档案断开后停止其主动桥，交回发现桥，不进入 30 分钟盲等。

发现桥的连接成功路径已经存在：`registerBluetoothBridgeIfNeeded` 在 `ready` 时按 identifier 查找档案，找不到才创建。共享发现阶段必须保证已有档案优先复用。

### 5.3 手动恢复

第一阶段不新增页面控件，复用现有“立即重新连接”按钮：

- 触发选中档案的立即尝试；
- 同时开启一次有界的已知档案查找窗口，例如 20–30 秒；
- 窗口内尝试系统已连接候选和发现桥可见的已登记设备；
- 窗口结束后回到 `waiting`，不继续无限重试；
- 状态文字显示正在查找或等待设备。

这是最小手动入口。它不改变页面布局；如果产品把按钮语义或状态文案也算页面修改，则先进入 HTML 设计评审，确认后再实现。

后续页面阶段可以增加“其他已登记遥控器”入口：

- 列出未连接的历史档案；
- 显示上次发现/连接时间和当前状态；
- 提供连接、停止自动连接、恢复自动连接、忘记设备；
- 忘记设备前必须确认，并保留映射导出能力。

### 5.4 失败设备退避

共享发现桥也需要防止坏设备反复占用：

- 同一设备连续握手失败时按 1、5、15、30 分钟退避；
- 失败状态只保存在当前进程，不写入用户配置；
- 超过阈值后停止自动尝试，等待用户手动操作；
- 退避只影响该设备，不阻塞其他设备发现；
- 日志只记录失败类别和次数，不记录原始设备标识。

这解决“坏设备永远不回来，但不能无限重试”和“幽灵设备阻塞真实第二只遥控器”的冲突。

### 5.5 发现桥的电源边界

共享发现不能变成新的后台扫描源：

- 继续使用现有发现桥的扫描和系统挂起逻辑；
- 系统睡眠、会话挂起或屏幕休眠时停止扫描；
- 不增加空闲扫描占空比；
- 不引入 DarkWake 期间的新主动扫描；
- 真实睡眠/唤醒和功耗影响列入验收，不以“发现桥原本就在扫描”代替测试。

## 6. 日志与诊断

- 主动连接只记录开始和结果，每次尝试一条汇总；
- `waiting` 和被动发现阶段不产生 `BLE CONNECT TIMEOUT`；
- 发现桥每 60 秒输出一条汇总，包含发现数、交接数、失败数，不逐设备记录；
- 已有 `ADOPT IGNORED` 聚合继续保留，不增加逐设备刷屏；
- 诊断字段只记录：角色、触发原因、尝试序号、恢复窗口剩余、最后成功/发现相对时间、失败类别、是否选中、是否允许自动连接；
- 不记录设备 UUID、HID 指纹、系统设备名或用户内容。

## 7. 兼容性和数据

- 不删除档案、identifier、HID 指纹或映射；
- 不新增必需持久化字段；如后续增加“自动连接”开关，必须可选解码，旧配置默认允许自动连接；
- Apple Siri Remote 和 Chromecast 不创建小米 BLE 桥，不受本方案影响；
- 多遥控器同时在线、按键路由和语音链路保持不变；
- 选中档案的语音键路径不能因为共享发现而增加首个响应延迟；
- 方案回滚只需恢复连接协调逻辑，不需要数据迁移。

## 8. 验收

### 自动化

- 选中档案：6 次有限重试后进入 `waiting`；手动触发重新开启窗口；重复触发有最小间隔。
- 非选中档案：不产生主动连接；发现后交接并复用原 profile/mappings。
- 档案断开：停止主动桥并交回发现桥，不进入 30 分钟盲等。
- 失败设备：1/5/15/30 分钟退避；超过阈值等待手动操作；不影响其他设备。
- Apple/Chromecast：现有路径不回归。
- 日志：无设备标识；无逐设备刷屏；等待阶段无连接超时日志。
- 睡眠/挂起：发现桥停止扫描，恢复后按现有系统路径重建。

### 真实设备

- RC003 选中并保持 Ready，RC001 离线 10 分钟：旧档案零主动连接，日志无每分钟超时，RC003 语音和按键正常。
- RC001 开机或回到范围：发现桥接入，卡片恢复，原映射和 HID 绑定不变；记录从设备可见到 Ready 的实际耗时。
- RC001 再次离线：停止主动连接，不产生新超时。
- 选中 RC003 断开：有限次数恢复，之后进入等待；按语音键和“立即重新连接”能重新尝试。
- 第二只真实 RC001/RC003 与选中设备同时存在：两台都能发现，互不覆盖映射。
- 坏设备或幽灵广播：有限退避，不阻塞真实设备。
- 系统睡眠/唤醒、蓝牙关闭/打开、App 重启：不增加连接风暴。
- 真实长时间离线、语音首字延迟和尾音完整性按跨硬件合同单独验收，不用单元测试替代。

## 9. 开发顺序和页面门禁

1. 本设计文档先由 Codex/维护者评审，确认状态模型、有限恢复参数、共享发现和手动入口。
2. 如评审通过，先实现连接引擎和自动化测试；页面不做改动时，继续使用现有“立即重新连接”按钮。
3. 如需增加“其他已登记遥控器”列表、停止自动连接或忘记设备，先提供 HTML 设计稿，覆盖中文/英文、浅色/深色、空状态、等待状态和操作确认。
4. HTML 设计稿经用户确认后，才开发 SwiftUI 页面。
5. 页面实现后补生产运行截图、真实设备验收和测试手册。

## 10. 待确认决策

- 选中档案的 6 次/约 2.5 分钟恢复预算是否合适，还是需要更短/更长。
- 第一阶段是否只复用现有“立即重新连接”按钮，还是同时进入“其他已登记遥控器”页面设计。
- 是否需要在第一阶段加入“停止自动连接”，还是留到页面阶段。
- 长期未发现设备的提示阈值和文案。
- 真实 RC001/RC003 关机、离开范围、仅系统 HID 连接三种状态下的发现行为，需要真机确认。
