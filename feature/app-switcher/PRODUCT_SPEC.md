# 应用切换器产品规范

## 适用范围

本规范约束 macOS 上用遥控器操作系统 `Command-Tab` 切换器的用户可见行为：进入会话、会话内的按键语义、确认与取消、自动退出，以及明确不做的能力。验证方法和通过/失败证据由 [`Testing/AppSwitcherRemoteControl.md`](../../Testing/AppSwitcherRemoteControl.md) 定义；本规范只定义行为本身。

HID 遥控器（RC001、RC003 等）与苹果遥控器共用同一套会话语义；苹果遥控器在 `BridgeAppModel` 有自己的触摸与按键入口，平台差异见文末。Windows 端可参考同一模型，但由独立实现承载。

## 用户问题与目标

用户在 Mac 上切 App 时不想放下遥控器去摸键盘。目标是用尽量少的手指动作完成「打开切换器 → 选择 → 确认」或「放弃」，并且任何时刻退出会话都不能把 `Command` 留在按下状态。

不使用自制 App 列表替代系统切换器：App 列表、空间、窗口缩略图和最小化窗口恢复都由 macOS 负责。

## 会话生命周期

1. **进入**：单击绑定为「切换 App」的按键后，合成并保持 `Command` 按下，发送一次 `Tab`，系统切换器出现且不立即完成切换。
2. **会话期间**：按键语义完全由会话接管，不再读取映射层的双击、长按配置；映射层的双击/长按动作在会话内不执行。
3. **前进**：任何单击绑定为「切换 App」的按键再按一次，等于在 `Command` 仍按住时再按一次 `Tab`，高亮移动一格。
4. **确认**：OK 键先按下 `Option`、再释放 `Command`、最后释放 `Option`，让全部窗口最小化的目标 App 恢复最近一个最小化窗口。
5. **取消**：返回键在 `Command` 仍按住时先发 `Escape`，再释放 `Command`。
6. **其他按键**：同样先 `Escape` 再释放 `Command`，并且**不执行该键自身动作**；会话退出对所有按键给出可见、可预期的反应。
7. **自动退出**：最后一次操作后 15 秒无输入，自动 `Escape` 并释放 `Command`。
8. **异常退出**：遥控器断连、监听停止、辅助功能或输入监控权限失效、前台 App 异常变化时释放 `Command`；用户用鼠标点击别处导致系统自己关掉切换器时只释放 `Command`，不补 `Escape`，避免落在前台 App 上。

进入会话的时机由映射层的手势判定决定：绑定键同时配置了双击或长按时，单击动作要等双击窗口（300ms）结束才提交，因此会话在松手后约 300ms 才真正打开。这是映射层手势语义，不属于本会话自己的规则。

## 会话内按键语义

| 按键 | 行为 | 说明 |
| --- | --- | --- |
| 绑定「切换 App」的按键（单击动作） | 发送下一次 `Tab` | 含 TV，但只在它确实绑定为「切换 App」时；不再有无条件的 TV 特例 |
| ← / → | 原生左右方向键 | 先带 `Command` 发送；macOS 14+ 上方向键不移动高亮时，自动改用 `Tab` / `Shift-Tab` 循环，并在本次会话内保持 |
| ↑ / ↓ | 进入目标 App 的窗口选择 | 统一发 `Command-↓` 进入；目标只有单一标准窗口时跳过窗口层，直接激活 App；进入后方向键按普通按键发送 |
| OK | 确认 | 窗口层里按 `Return` 打开高亮窗口；没有高亮时不响应，会话保持 |
| 返回 | 取消 | `Escape` + 释放 `Command` |
| 其他任何按键 | 结束会话 | `Escape` + 释放 `Command`，自身动作不执行 |

补充规则：

1. **按住连发**：←/→/↑/↓ 按住约 350ms 后每 100ms 移动一格，松开立即停止；启动键本身不因连发重复打开会话。
2. **绑定判定按单击动作**：只把「切换 App」绑在双击或长按上的按键，会话中按未绑定键处理（结束会话）。
3. **音量键**：结束会话，但音量键的原生事件仍由系统处理，音量会同时变化；这是可接受行为。
4. **语音键**：不经过本路由，按下不会结束会话（原因见下一节）。
5. **诊断日志**：会话入口写 `HID APP SWITCHER`，结束写 `ended reason=…`；未绑定键退出额外写 `ended_by button=… phase=session`。

## 明确不做

### 长按绑定键确认

提案希望「再按一次 = 下一个 App，长按 = 确认」。当前不做，原因是它与「按下即发送 Tab」直接冲突：

1. 按下瞬间已经发送 `Tab`，550ms 长按阈值到达时高亮已经移动，确认到的是**下一个** App，而不是用户按下时看到的那个。
2. 把 `Tab` 延后到松手可以消除冲突，但每次前进都要等一次完整的按键持续时间（通常 100–200ms），与「尽可能少的手指动作、即时反馈」的目标相反。
3. OK 键已经承担确认，并带最小化窗口恢复语义，长按确认没有提供新的能力。

要做必须先由产品在「下一项并确认」「延后 Tab」「换一颗键确认」三种方案中选定一种，不能按原提案直接实现。

### 语音键退出切换器

语音键不是普通遥控器按键：小米遥控器的语音键是 HID usage `0x3E`（F5）或 `0x0C`，系统 Fn 由 `MacMicrophoneVoiceKeyMonitor` 单独监听，两者都不在 `RemoteButton` 路由里。该监听是 listen-only 事件 tap，只能观察、不能消费。

因此：

1. 会话收不到语音键的按下，无法按「其他按键」规则结束会话。
2. 要让它只退出、不触发语音，必须改成主动事件 tap 拦截 Fn；这会影响系统听写和现有语音链路，风险和收益不匹配。
3. 若只做「语音开始时结束会话」，语音仍会启动，与提案「不执行原动作」不一致。

语音键与会话的关系留给语音链路单独设计。

### 上下键 300ms 去抖

会话内上下键同时存在离散按下和按住连发两条路径。把去抖放在按下层会与连发竞争，放在移动函数里会吞掉连发的第一步；300ms 又接近双击窗口，用户有意快速按两次会被静默丢掉，等于把「没有反应」换一种形式带回来。收益取决于遥控器手感，风险明确，暂不做。

若将来要做，只对离散按下生效、连发路径绕过，并保持每次被吞掉的按下仍然重置 15 秒超时。

### 其他边界

- 进入会话的 300ms 双击窗口：属于映射层手势语义，不在本规范内。
- 苹果遥控器的 TV 特例：`BridgeAppModel` 的独立会话仍把 TV 无条件当作 `Tab`，尚未与本文的「按绑定判断」对齐。
- 不做自制 App 列表、不读取切换器当前高亮项；macOS 没有公开 API，只能读取 Dock 的 `AXSelectedChildren`，且必须在进入窗口层前读取。

## 跨平台与硬件差异

| 范围 | 差异 |
| --- | --- |
| macOS 13（Intel） | 左右方向键通常直接移动高亮；确认后最小化窗口恢复依赖 Option/Command 的时序 |
| macOS 14+ | 方向键可能不移动高亮，会话在 250ms 核对后改用 `Tab` / `Shift-Tab` 循环 |
| 苹果遥控器 | 触摸圆周可移动选择；实体 OK/返回与本文一致；TV 按钮仍是无条件 `Tab` |
