# SayAll Onboarding 跨平台产品规范

## 文档地位

本文是无线麦SayAll.app Onboarding 的跨平台产品规范，也是检查、设计、修改和测试 Onboarding 时的唯一产品行为入口。

规范适用于现有 macOS 版本及未来 Windows 等桌面平台。平台实现必须先满足本文的产品不变量，再按平台附件实现权限、按键、音频、连接和界面差异：

- [macOS 平台适配](platform-macos.md)
- [Windows 平台适配](platform-windows.md)
- [开发接入点](development.md)
- [测试入口](testing.md)

本文使用以下约束词：

- **必须**：所有平台不得降低或绕过的产品要求。
- **应该**：除非存在经过记录的平台限制，否则应遵守。
- **可以**：平台可以根据系统能力选择的实现。

平台附件不能覆盖本文的“必须”要求。若产品不变量发生变化，必须先或在同一次修改中更新本文，再更新平台附件、实现、测试和截图证据。

## 产品目标

Onboarding 不是功能介绍或页面 Tour，而是首次可用性验收流程。

用户完成 Onboarding 时，产品必须已有证据证明：

1. 用户选择的控制来源能够真实连接并发送控制事件。
2. 语音会话能够由预期按键或操作开始和结束。
3. 真实音频已沿当前平台配置的路线到达目标语音工具。
4. 目标语音工具已把语音结果写入测试输入框。
5. 用户知道日常使用所需的语音键、音频设备和第三方工具配置。
6. 失败时，页面和诊断能够指出已经确认的失败边界以及下一步操作。

访问过页面、点击过按钮、收到过连接回调、音频已入队或用户勾选确认，都不能单独代表 Onboarding 成功。

## 非目标

Onboarding 不负责：

- 完整介绍所有高级功能或替代产品帮助中心。
- 在首次流程中提供完整按键映射编辑器。
- 读取第三方 App 的私有文件、数据库、沙盒、私有协议或未公开设置。
- 通过预设成功状态、测试桩或手动输入绕过真实端到端验证。
- 强制所有平台使用相同的系统权限名称、语音键或音频驱动实现。
- 因增加新平台而降低已有平台的完成门槛。

## 核心产品不变量

### 1. 不可跳过，但必须可恢复

- 未完成必要能力检查前，不提供“跳过”“稍后继续”或进入主页面的旁路。
- 关闭 App、系统重启或连接中断后，必须保存并恢复到合理的未完成位置。
- 卡住不能等于死路。每个失败状态必须提供与当前原因直接对应的主要修复操作。
- 用户必须能够返回前一步检查选择；返回不能立即被自动路由再次推回原页面。

### 2. 以真实能力状态推进

- 页面访问和按钮点击不是通过条件。
- 每一步必须根据当前实时能力状态决定能否继续。
- 同时存在多个控制来源时，只允许用户当前选择的来源满足连接、按键和语音门禁。
- 临时状态、旧会话结果和其他来源事件不得污染当前验证。
- 完成前必须重新检查仍会影响日常使用的权限、连接和音频条件。

### 3. 复用生产链路

- Onboarding 必须尽量复用日常运行时使用的连接、按键、音频、输入目标和语音会话链路。
- 不得为了让 Onboarding 通过而建立只存在于向导中的模拟成功路径。
- 测试工具可以注入状态或回放事件，但生产完成条件必须来自生产能力模型。

### 4. 配置必须在测试现场可见

端到端语音测试页必须在输入框附近集中显示：

- SayAll 当前发送的语音键或开始/结束操作。
- SayAll 当前使用的音频输出路线或设备。
- 第三方语音工具应配置的语音识别键或触发方式。
- 第三方语音工具应选择的麦克风或音频输入设备。
- 当前工具特有且会阻止语音输入的必要选项。

如果 SayAll 与第三方工具的按键或音频配置不一致，用户必须能够在开始测试前直接看出差异。已经可以自动观察的 SayAll 状态与只能由用户确认的第三方状态必须有明显区别。

### 5. 第三方状态必须诚实表达

- 只能通过公开 API、公开协议或用户可见界面获得第三方状态。
- 无法观察的第三方设置必须显示为“需要用户确认”或“未知”，不能显示为自动检查通过。
- 用户确认只能证明用户执行了核对，不能替代最终真实文字上屏。
- 切换语音工具、语音键或音频设备后，受影响的用户确认必须失效。

### 6. 最终成功必须由用户可见结果证明

语音测试至少必须确认：

1. 当前所选来源开始了语音会话。
2. 收到了非空的真实音频样本。
3. 音频被投递到当前选择且有效的路线。
4. 用户结束了同一次语音会话。
5. 第三方语音工具把文字写入当前测试输入框。

手动键盘输入、粘贴旧文字、其他窗口出现文字或上一 attempt 的迟到结果不能满足最终门禁。

## 标准流程模型

平台可以根据系统能力合并相邻页面或调整说明方式，但不得改变以下依赖顺序和完成语义。

### 阶段 A：准备

#### 欢迎与预期

- 说明本流程将完成真实设置和验证，而不是只展示教程。
- 不显示会鼓励跳过必要步骤的入口。
- 可以使用简短阶段导航，但不应制造“快速点完页面即可完成”的预期。

#### 选择语音工具

- 显示平台支持或已检测到的语音工具。
- 推荐工具未安装时，必须提供官方来源入口，不得用第三方下载地址代替。
- 选择“其他语音工具”时，必须明确要求该工具支持语音输入，并允许用户自行配置触发键和麦克风。
- 选择结果必须进入后续配置核对和诊断上下文。

#### 选择控制来源

- 优先展示产品主控制来源；没有主设备时提供当前平台支持的替代来源。
- 必须明确区分“当前是否拥有设备”和“选择哪种替代控制方式”。
- 已经由生产状态确认主设备可用时，可以减少不必要的选择步骤，但不能为判断而提前触发权限或扫描。

### 阶段 B：设置

#### 权限

- 只请求当前产品链路真正需要的系统权限。
- 必须解释权限用于哪项用户功能，并展示实时授权状态。
- 已授权项目仍应该允许用户打开对应系统设置进行检查或恢复。
- 拒绝、受限、需要重启和权限历史异常必须有不同的恢复指引。

#### 连接与普通控制验证

- 必须确认当前选择的控制来源真实连接。
- 至少观察一个来自该来源的真实普通控制事件，避免把系统设备列表中的“已连接”误当成产品可用。
- 连接、协议准备和事件可用性如果是不同边界，必须分别记录。

#### 音频路线

- 必须选择当前平台支持且能够把无线麦音频提供给第三方语音工具的路线。
- 页面必须区分 SayAll 的音频输出端与第三方工具的麦克风输入端，并要求两端匹配。
- 设备存在、已选择、实际绑定、正在投递和已经排空是不同状态，不能用一个布尔值替代全部事实。
- 不满足语音输入用途的扬声器或普通输出设备不能通过门禁。

### 阶段 C：试一下

#### 配置核对与真实语音文字测试

- 在测试输入框页显示完整配置核对卡。
- SayAll 可自动观察的配置应直接显示当前值与正常/异常状态。
- 第三方不可观察的配置必须逐项要求用户确认。
- 未完成配置核对、SayAll 自身配置异常或音频路线失效时不能完成流程。
- 即使所有确认均已勾选，仍必须完成一次真实语音到文字的端到端验证。

#### 普通按键体验

- 使用当前选择的控制来源验证多个不同普通按键或等价控制操作。
- 重复同一个按键不能伪装成多个独立能力已经可用。
- 语音键不应被计入普通按键体验。

#### 完成

- 完成页必须重新确认关键运行条件仍然成立。
- 条件退化时应返回最接近问题的修复步骤，而不是清空整个流程。
- 完成后进入主页面，并保存当前 Onboarding 流程版本。

## 页面与交互要求

- 每个页面只突出当前最重要的任务和一个主要修复动作。
- 必要配置、错误和继续条件必须直接显示，不能只放在悬停提示、弹窗或帮助文档中。
- 能在当前页面完成的选择和确认应平铺展示，避免连续弹窗和深层菜单。
- “继续”按钮的禁用原因必须能够从当前页面状态理解。
- 所有用户可见文本必须支持平台要求的辅助功能、键盘导航、屏幕阅读和缩放。
- 中文界面文字不得小于项目规定的最小字号；其他平台也必须制定等价的可读性门槛。
- 浅色、深色、高对比度和系统缩放下不能裁切主要任务、状态、输入框或导航。

## 状态、持久化与升级

必须持久化：

- Onboarding 流程版本。
- 是否完成当前流程版本。
- 当前合理恢复步骤。
- 用户选择的语音工具和控制来源。
- 平台适配明确要求保留的非敏感配置。

不得把临时会话状态持久化为已经通过，例如当前连接回调、按键按下状态、音频样本、输入框文字或某次 attempt 的成功标志。

升级规则：

- 已安装用户不能仅因加入 Onboarding 而被误判为全新用户。
- 产品新增真正必要的能力门禁时，使用流程版本决定补跑范围。
- 权限或设备在完成后失效时，应优先进入定向修复，而不是强制重跑全部步骤。
- 用户主动重新运行 Onboarding 时，不得清除连接资料、按键映射、音频选择和其他无关设置。

## 失败、恢复与诊断

每个步骤必须定义：

- 已确认事实。
- 当前未知边界。
- 稳定失败原因码。
- 用户可以执行的下一步。
- 重试、取消、返回、断连和 App 重启后的状态。

日志必须遵守仓库根目录 [`LOGGING.md`](../../LOGGING.md)，覆盖从用户操作到最终可见结果的完整链路。语音 attempt 必须有唯一标识和唯一终态，并区分：

- 控制触发没有发生。
- 会话未开始或未结束。
- 没有收到音频。
- 音频路线、绑定或播放失败。
- 输入目标未准备好或持续失焦。
- SayAll 可观察链路正常，但第三方工具没有提交文字。

第三方内部状态不可观察时，诊断必须明确 `observable=false` 或等价边界；用户确认与自动观察不得使用同一字段语义。

## 隐私与跨应用边界

Onboarding 不得记录或导出：

- 用户说出的音频或可恢复音频的样本。
- 测试输入框文字、长度或上下文。
- 用户身份、设备身份、路径、窗口标题、文档名或凭据。
- 第三方 App 私有文件、数据库、沙盒、内部设置或未公开协议数据。

允许记录稳定枚举、布尔状态、脱敏计数、耗时、平台版本、App 版本、流程版本、失败边界和用户是否完成某项确认。完整要求以 [`LOGGING.md`](../../LOGGING.md) 为准。

## 平台适配契约

每个平台附件必须明确以下映射：

| 产品能力 | 平台附件必须回答的问题 |
| --- | --- |
| 控制来源 | 支持哪些真实设备、手机或网页来源，如何证明当前来源可用？ |
| 权限 | 每项权限对应什么能力，拒绝和恢复路径是什么？ |
| 语音触发 | SayAll 发出什么按键或操作，第三方工具如何配置为一致？ |
| 音频路线 | SayAll 输出端是什么，第三方工具输入端是什么，如何证明投递成功？ |
| 输入目标 | 如何确认文字会进入当前测试输入框？ |
| 第三方状态 | 哪些可以公开观察，哪些只能由用户确认？ |
| 持久化 | 平台保存哪些选择，升级时如何迁移？ |
| 日志 | 哪些边界可以自动确认，哪些必须记录为未知？ |
| UI 与辅助功能 | 最小窗口、缩放、键盘导航和屏幕阅读如何验收？ |
| 真实验收 | 哪些必须使用真实设备、系统权限和第三方 App？ |

平台不支持某项现有实现时，必须提供实现同一产品目标的等价能力，或明确缩小该平台公开支持范围；不能静默跳过门禁。

## 验证分层

Onboarding 修改必须同时考虑以下四层：

1. **流程自动化**：状态机、分支、持久化、门禁、失败恢复、旧配置迁移和来源隔离。
2. **完整 UI 与截图**：所有受影响页面、控制来源、工具分支、浅色/深色、主要语言、最小窗口和缩放。
3. **构建与产物**：目标平台构建、架构、签名、安装、升级和启动。
4. **真实环境**：真实权限、控制设备、音频路线、第三方语音工具、前后台、断连和最终文字写入。

前一层通过不能替代后一层。交付说明必须明确哪些层已经通过、哪些仍待现场验收。

## 变更检查清单

检查或修改 Onboarding 前：

- [ ] 已完整阅读本文和当前平台附件。
- [ ] 已确认本次变更属于跨平台产品规则还是单个平台适配。
- [ ] 已画出从用户动作到最终可见结果的逻辑链路。
- [ ] 已列出受影响页面、能力门禁、持久化、日志和恢复路径。

提交前：

- [ ] 产品不变量变化已更新本文。
- [ ] 平台行为变化已更新对应平台附件。
- [ ] 测试手册覆盖成功、拒绝、失败、重试、返回、重启和升级边界。
- [ ] 所有受影响的完整流程与分支已完成截图检查。
- [ ] 日志能区分确定事实、用户确认、未知边界和最终结果。
- [ ] 未读取或记录第三方私有状态和用户敏感信息。
- [ ] 已明确自动化、截图、模拟环境和真实设备验收边界。
