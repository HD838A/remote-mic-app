# 功能开发档案

`feature/` 用于记录已经进入正式开发的新功能。每个功能使用独立子目录，保存可公开的开发原因、功能行为、实现过程、测试方法和验证边界，让后续开发、评审和回归不依赖聊天记录。

本目录不替代根目录 [`TODO.md`](../TODO.md)。TODO 继续记录任务状态和优先级；功能档案负责说明功能是如何设计、实现和验证的。详细 research、长期计划、竞品分析和内部产品判断继续保存在私有 marketing 仓库，不复制到这里。

## 目录规范

每个功能使用 kebab-case 目录名：

```text
feature/
  README.md
  <feature-name>/
    README.md
    development.md
    testing.md
```

必备文件：

- `README.md`：为什么开发、用户功能介绍、范围、非目标、隐私与兼容边界、当前状态。
- `development.md`：需求来源、实现切片、关键决策、精确代码接入点、提交和验证证据、已知限制。
- `testing.md`：测试准备、逐步操作、预期结果、失败判定、回归范围和人工验收边界。

如果功能后续产生独立协议、迁移或发布说明，可以在同一目录增加文件，但不要把详细私有研究复制进公开仓库。

## 状态要求

- `开发中`：代码或验证尚未形成完整闭环。
- `等待人工验收`：自动化和构建已通过，但真实硬件、第三方 App 或用户流程尚未验收。
- `已完成`：功能实现及要求范围内的自动化和人工验收均完成。
- `已停止`：实验未达到继续条件；必须记录停止原因和保留内容。

功能状态变化时，应同步更新功能首页和测试手册中的验证记录。没有真机或真实用户流程证据时，不能标记为已经完成真机验收。

## 新功能模板

创建新目录时至少回答：

1. 用户遇到了什么问题，为什么现在开发？
2. 用户可以看到和操作什么？
3. 本次明确做什么、不做什么？
4. 数据会读到哪里、发送到哪里、保存在哪里？
5. 修改了哪些文件和共享链路，为什么？
6. 开发中遇到了什么关键问题，最终如何处理？
7. 自动化、构建、真机和第三方 App 分别验证到什么边界？
8. 用户应按照什么步骤测试，什么结果属于失败？
