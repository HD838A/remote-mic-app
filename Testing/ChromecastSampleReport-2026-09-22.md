# Chromecast 样机记录：2026-09-22 接入的这只（按键通道不可用）

本文只记录**这一只**样机的身份信息、判定结论与取证方法。它是一只**按键不可用**的设备样本，
不代表、也不改变此前各只样机的结论。

---

## 1. 设备身份

| 项目 | 值 |
| --- | --- |
| 系统名称 | `Chromecast Remote` |
| 系统地址 | `0C:EC:80:F8:E9:9E` |
| VID / PID | `0x18D1` / `0x9450` |
| **固件版本（系统侧读出）** | **`26.7`** |
| 传输 | Bluetooth Low Energy（`Transport = BT-AACP`） |
| 设备自报电量 | 100% |
| 系统标注类型 | `Minor Type: Keyboard` + `Minor Type: Headphones` |
| HID 主用途 | `usagePage = 12`（Consumer Page）/ `usage = 1`（Consumer Control） |
| HID `locationID` | `0x59249D3A` |
| 注册表实例（`hidutil`） | 每次重新配对都会换新：`0x10007B2F1` / `0x10007B2F5` → 重配后 `0x10007B911` / `0x10007B915` |

读出方式：`system_profiler SPBluetoothDataType`（名称、地址、固件、类型、电量）、
`hidutil list | grep 9450`（用途、locationID、注册表实例）。

---

## 2. 结论

**这只样机的按键上报通道事实上不可用。**

链路层完全正常——蓝牙连得上、ATVV/GATT 能完成能力协商、电量 100%、按键的 HID 服务也由系统建好了；
但**按键报告基本发不出来**：一天中链路建立了 16 次，用户按了几十次键，最终只上报 2 次。

判定为**设备侧故障**，建议退换货。宿主（我们的 App）与协议实现均无责，依据见 §3。

---

## 3. 判定依据

### 3.1 历史基线对比（最直接的一条）

把日志目录下的 4 个文件合并（`runtime.log` 及其轮转文件 `.1` `.2` `.3`），
按天统计 `CHROMECAST HID press` 的出现次数：

| 日期 | 上报次数 | 说明 |
| --- | --- | --- |
| 2026-09-16 | 62 | 链路可正常工作时的量级 |
| 2026-09-18 | 17 | 同上 |
| 2026-09-19 | 53 | 同上 |
| 2026-09-21 | 3 | |
| 2026-09-22 | **2** | **本只**：当天链路建立 16 次、用户按键数十次 |

09-22 的两条分别是 `04:55:34Z select` 与 `12:38:36Z volume_down`（UTC，本地 +8）。

> 日志按「按键变化」记录，同一次按住期间的重复报告不会重复成行；因此这个计数是**下界**，
> 不影响「本只几乎没有上报」的判断。日志中系统名相同的多只样机无法按名字区分，
> 但「链路正常时每天能有几十次上报」这个量级可作为基线。

### 3.2 独立观察进程（排除宿主 App 与我们自己的代码路径）

用一个**与宿主 App 无关**的小程序观察：`IOHIDManager` 按 VID/PID 匹配、
**以观察模式打开（不独占）**、每条输入报告打时间戳、每 10 秒一条心跳；**不启动宿主 App**。

同一进程同时观察被试与一只已知正常的对照设备，结果：

| 设备 | 探针结果 |
| --- | --- |
| **被试** `0x18D1`/`0x9450` | 连续 2.5 分钟、16 次心跳，全部 `reports=0`；期间用户按了 YouTube / Netflix / 音量- 并做过 3 秒长按 |
| **对照** 小米遥控器 `0x2717`/`0x32B8` | `REPORT #1 id=1 len=7 bytes=[01 00 00 80 00 00 00]` → `REPORT #2 … [01 00 00 00 00 00 00]`（按下 + 抬起） |

对照设备有报告、被试设备零报告 ⇒ 观察手段本身有效，被试设备确实没有发出任何报告。

> **取证时的坑**：用 shell 后台方式（`nohup … &`）启动的探针会随该条命令结束被一并收走。
> 必须先确认**心跳行出现**，否则日志里的「零报告」是假阴性。

### 3.3 系统侧同样收不到

同一时段按音量键，**macOS 无音量 HUD、音量无变化**——此时宿主 App 未运行、探针也没有独占设备。
即：不是「只对我们不发」，而是**对系统也没有发**。

### 3.4 各种复位手段均无效

| 手段 | 结果 |
| --- | --- |
| 取出电池约 5 秒后装回 | 无效 |
| 系统蓝牙「移除设备」→ Home + Back 重新配对 | 无效（重配后 HID 服务实例为全新，仍零报告） |
| Mac 关开蓝牙 | 无效 |
| 长按任意键约 3 秒（用于唤醒深度休眠） | 无效 |
| 官方恢复出厂（见 §5 第 1 条） | **未执行**（执行当时尚不知道该流程与本仓习惯做法不同） |

### 3.5 故障发生前的最后一次上报：只有按下、没有抬起

```
12:38:36.788Z  CHROMECAST HID press usage=0x0d control=volume_down
               （之后 13 秒内：没有任何事件）
12:38:49.864Z  CHROMECAST CONTROL cancelled control=volume_down reason=disconnected
```

宿主一直停在「按住」状态，直到用户扣电池断开链路。**macOS 对处于按住状态的音量键会自动重复**，
因此音量条一直动、停不下来。这不是遥控器在重发，也不是宿主在重发——宿主日志只在按键变化时成行，
所以日志里只有一条按下。

## 4. 附带发现（对本型号普遍成立，值得记下）

1. **音量 / 电源键历史上也极少上报**：2026-09-05 ~ 09-20 共 132 条按键报告中，
   `select` 40、`right` 30、`left` 18、`mute` 10、`down` 10、`up` 6、`back` 5、`input` 2、
   **`volume_down` 5、`volume_up` 3**、`youtube` 1、`netflix` 1。
   与公开资料一致：Google TV 遥控器的**音量与电源键主要走红外**（面向电视），蓝牙侧只在部分情形上报。
   → **不要把音量 / 电源键当作可靠的可映射键**。
2. **「按下无抬起」的后果由系统承接**：音量连发是 macOS 的自动重复行为，
   宿主侧无法阻止。宿主的兜底（超时补一个抬起）只能释放宿主自己的按住状态。

## 5. 「已连接但不上报」的恢复手段（备查）

1. **官方恢复出厂**（与「取电池 5 秒」不是一回事，本仓尚未实测，来源为 Google 支持文档经第三方整理）：
   ① 取出两节电池后**静置约 5 分钟**；② **一直按住 Home 键**的同时把电池装回；
   ③ 继续按住，直到指示灯**先常亮、再转为脉动**，此时松手；④ 进入配对模式后重新配对。
   适用于 Chromecast with Google TV 语音遥控器；新款 Google TV Streamer 遥控器的复位方式不同。
2. 取出电池约 5 秒后装回（本仓习惯做法，见效快）。
3. 系统蓝牙「移除设备」后重新配对（Home + Back 3~5 秒进入配对模式）。
4. 闲置数分钟后按键无反应属**深度休眠**：长按任意键约 3 秒唤醒（唤醒期的第一个按键会被设备自己消耗）。

---

## 6. 未定论 / 待确认

- 本只是**出厂即有的硬件故障**，还是「固件在丢失抬起后卡死」——复位手段全部无效更支持前者，但未有定论。
- 官方恢复出厂流程本仓**未实测**。
- 本只的失败是否与宿主的独占（`seize`）有关：**不支持**该假设（App 未运行、探针不独占时同样零报告），
  但不能完全排除。

## 7. 复现与取证速查

```
# 设备身份（名称 / 地址 / 固件 / 电量 / 类型）
system_profiler SPBluetoothDataType | sed -n '/Connected:/,/Not Connected:/p'

# HID 服务与用途（用途、locationID、注册表实例）
hidutil list | grep 9450

# 按键上报次数（含轮转日志）
cd ~/Library/Logs/RemoteMic
cat runtime.log.3 runtime.log.2 runtime.log.1 runtime.log | \
  grep -a "CHROMECAST HID press" | grep -aoE "^[0-9]{4}-[0-9]{2}-[0-9]{2}" | sort | uniq -c

# 宿主侧按键事件（判据关键字）
grep -aE "CHROMECAST HID (press|release)|CHROMECAST ACTION|CHROMECAST CONTROL" runtime.log
```

**独立观察进程的要点**（用于区分「设备没发」与「宿主没接好」）：
`IOHIDManager` + 按 VID/PID 匹配 + **观察模式打开（不独占）** + 每条报告打时间戳 + 10 秒心跳；
必须**同时挂一只已知正常的设备作对照**；必须**先确认心跳行出现**再采信「零报告」。
