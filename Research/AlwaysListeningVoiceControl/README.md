# 免按键持续语音控制可行性研究

- 研究日期：2026-08-01
- 当前仓库基线：Remote Mic 1.4.11 (35)，提交 a965d19
- 目标系统：macOS 15 或更高版本，仅支持 Apple Silicon
- 目标体验：无需按遥控器按键，直接说“打开 Codex”等命令即可执行操作

本文研究的是持续待命的语音命令入口。功能应优先复用 macOS 已有能力；只有系统方案不能满足产品体验时，才考虑在无线麦中加入常驻语音识别。RC003 能否由主机无按键主动开麦另见 [RC003 无按键持续收音研究](../RC003ContinuousAudio/README.md)。

## 结论摘要

1. **这个想法可以实现，而且 macOS 15 已经内置了第一种实现。** Apple 的“语音控制”可以持续听取命令、打开 App、操作界面、听写文字，并支持自定义命令和运行快捷指令。
2. **第一阶段不需要开发，也不需要购买专用设备。** 使用 Mac 内置麦克风或普通 USB 麦克风，打开系统“语音控制”后即可测试“打开 Codex”。如果系统不能直接识别 Codex 名称，可创建一个打开 Codex 的快捷指令，再绑定自定义语音命令。
3. **RC003 的正常按键行为不是持续收音，但无按键主动开麦尚未被排除。** 真机日志只证明“按住开始、松开停止”的产品路径；Infineon 官方 ATVV 参考固件同时证明主机存在主动 `MIC_OPEN` 命令，v1.0 还定义了 `MIC_EXTEND`。RC003 是否接受以及能否长期续期必须通过受控真机实验确认。
4. **无线麦内置持续语音模式也可实现，但工作量明显更大。** 持续采集音频、唤醒词、命令识别、误触发控制、权限、功耗和隐私提示都需要独立设计。
5. **不能把 Apple 传统 Speech API 直接当作无限监听器。** Apple 对 `SFSpeechRecognizer` 的说明包含单次音频约一分钟限制、识别服务限流、网络和电量负担。即使循环重启任务，也不能据此承诺可靠的 7×24 小时监听。
6. **若开发 App 内模式，推荐“本地唤醒词 + 短时命令识别”。** 低功耗组件只判断是否听到唤醒词；确认唤醒后再开启几秒钟的命令识别，并且只执行白名单动作。

## 方案对比

| 方案 | 开发量 | 是否能持续待命 | 离线能力 | 当前判断 |
| --- | --- | --- | --- | --- |
| macOS 15 系统“语音控制” | 无或极少 | 是 | 首次下载后可离线 | 首选，先做零开发真机验证 |
| 无线麦直接循环使用 `SFSpeechRecognizer` | 中等 | 不可靠 | 取决于语言和设备是否支持本地识别 | 不作为正式架构 |
| 无线麦内置本地唤醒词，再短时识别命令 | 较大 | 是 | 可以设计为完全本地 | 第二阶段候选 |
| 专用 USB 麦克风配合系统或 App | 硬件成本低，软件工作不变 | 是 | 由识别方案决定 | 可改善拾音、静音和隐私提示 |
| RC003 主动 `MIC_OPEN` + `MIC_EXTEND` | 小到中等 | 协议上存在路径，真机未确认 | 由识别方案决定 | 仅作为实验性候选 |
| 独立语音助手硬件或云端中继 | 很大 | 是 | 通常依赖网络 | 当前没有必要 |

## Apple 官方能力

### macOS 15“语音控制”已经能完成核心需求

Apple 的 [macOS 15《在 Mac 上开始使用“语音控制”》](https://support.apple.com/zh-cn/guide/mac-help/mchl1a04f324/15.0/mac/15.0)明确说明：

- 可以通过声音导览桌面和 App、与屏幕内容交互、听写和编辑文本；
- 官方命令示例包含“打开邮件”；
- 首次启用需要联网下载 Apple 提供的内容；
- 下载完成后，无需互联网连接即可使用。

[《使用“语音控制”命令与 Mac 交互》](https://support.apple.com/zh-cn/guide/mac-help/mh40719/mac)还说明：

- 只需直接说出命令即可执行；
- 可以说“停止听取”和“开始听取”暂停或恢复；
- 可以切换到“命令模式”，让非命令内容被忽略，减少把日常讲话误输入文本框的风险。

[macOS 15《在 Mac 上自定义“语音控制”》](https://support.apple.com/zh-cn/guide/mac-help/mchl9899c8a5/15.0/mac/15.0)确认：

- 可以选择用于听取命令的麦克风；
- 可以打开或关闭标准命令；
- 可以创建自定义命令；
- 自定义命令可以按键盘快捷键或运行“快捷指令”；
- 自定义命令可以限制为所有 App 或某个指定 App；
- Apple 建议命令使用两个或更多字词，并避免容易与其他命令混淆的名称。

因此，“打开 Codex”有两条无需修改无线麦的路径：

1. 直接尝试系统标准的“打开 + App 名称”命令；
2. 如果 Codex 名称识别不稳定，建立“打开 Codex”快捷指令，再创建两字以上且不易混淆的自定义语音命令运行该快捷指令。

### Apple Speech framework 可以识别实时音频，但不适合直接无限监听

Apple [Speech framework](https://developer.apple.com/documentation/speech)支持识别录音或实时音频，并指出语音命令是其适用场景之一。旧版 [`SFSpeechRecognizer`](https://developer.apple.com/documentation/speech/sfspeechrecognizer)从 macOS 10.15 起可用，因此满足本项目 macOS 15 的部署目标。

但 Apple 同一文档明确提醒：

- 某些语言可能需要互联网连接；
- 识别服务会对单台设备和 App 的请求量实施限制；
- 单次音频时长应按约一分钟限制设计；
- 语音识别会带来较高的电量和网络负担；
- App 应明确提醒用户当前正在录音。

`supportsOnDeviceRecognition` 只能用于判断当前识别器是否支持本地识别，不能保证所有语言、设备和识别场景都可离线，也不能消除单次任务生命周期和持续运行可靠性问题。

macOS 26 新增的 `SpeechAnalyzer`、`SpeechDetector` 等能力不能作为本项目唯一实现，因为项目已经决定最低支持 macOS 15。

### 权限要求

如果由无线麦直接采集麦克风：

- Apple 要求在 Info.plist 中提供 [`NSMicrophoneUsageDescription`](https://developer.apple.com/documentation/bundleresources/information-property-list/nsmicrophoneusagedescription)，向用户解释为什么访问麦克风；
- 如果使用可能把数据发送到 Apple 语音识别服务器的 API，还需要 [`NSSpeechRecognitionUsageDescription`](https://developer.apple.com/documentation/bundleresources/information-property-list/nsspeechrecognitionusagedescription)；
- 当前应用只有蓝牙权限说明，没有麦克风和语音识别权限说明，因此 App 内模式需要新增权限流程。

## 音源选择

### Mac 内置麦克风

优点：

- 不需要额外硬件；
- 与系统“语音控制”直接兼容；
- 适合先验证命令识别和实际使用价值。

风险：

- 距离远、环境噪声或扬声器回声可能增加误识别；
- 缺少独立的实体静音状态；
- 用户可能不容易判断当前是否正在监听。

### 普通 USB 麦克风

推荐优先选择带实体静音键和明显工作指示灯的型号。它并不会自动提供语音识别能力，但可以改善：

- 远距离拾音；
- 环境降噪；
- 物理静音；
- 用户对持续收音状态的感知。

不需要设计专有 USB 设备。只要它在 macOS 中显示为标准音频输入设备，系统“语音控制”或未来的 App 内模式就可以选择它。

### RC003

暂不作为首选持续音源，但不能再判定为硬件层面绝对不支持。现有 App 只在遥控器发出 `START_SEARCH (0x08)` 后才写入 `MIC_OPEN (0x0C)`，所以过去的真机测试从未覆盖“完全不按键，由 Mac 主动先发 `MIC_OPEN`”这一条路径。

Infineon 官方 Android TV 语音遥控器参考固件把 `MIC_OPEN`、`MIC_CLOSE`、`MIC_EXTEND` 明确标为主机到遥控器的命令，并在收到 `MIC_OPEN` 后启动音频传输。这证明协议允许主机发起会话，但不能代替 RC003 真机验证。即使短时主动开麦成功，还要确认硬件传输超时、`MIC_EXTEND` 续期、休眠、续航和持续监听指示。

## 与当前无线麦代码的衔接

当前 `ButtonAction` 已经定义打开 Codex、Claude、cmux、微信、Cursor、Xcode、Slack、Chrome、Safari 等动作。`KeyboardInjector` 已经通过 `NSWorkspace.openApplication` 打开目标 App，并对 Codex、Claude 和 cmux 执行输入区域聚焦。

因此，未来 App 内语音控制不需要重新实现命令执行层。最小边界是新增：

1. 麦克风输入和监听状态；
2. 本地唤醒词或语音活动检测；
3. 短时命令识别；
4. 文本命令到现有 `ButtonAction` 的白名单映射；
5. 监听指示、暂停、权限和误触发保护。

不应让识别文本直接拼接成 shell 命令，也不应默认支持任意脚本执行。

## 推荐分阶段路线

### 阶段 0：零开发验证

在一台 macOS 15 Apple Silicon Mac 上：

1. 打开“系统设置 → 辅助功能 → 语音控制”；
2. 完成语言内容的一次性下载；
3. 选择 Mac 内置麦克风或 USB 麦克风；
4. 切换到“命令模式”，避免普通讲话被写入文本框；
5. 尝试说“打开 Codex”；
6. 若失败，创建一个打开 Codex 的快捷指令，并创建自定义语音命令运行它；
7. 再测试打开 Claude、cmux、Safari 和无线麦；
8. 测试“停止听取”和“开始听取”。

这一阶段如果已经满足实际需求，应优先编写使用说明，而不是在无线麦中重复实现系统功能。

### 阶段 1：无线麦提供系统方案引导

若零开发验证成功，但配置过程不够直观，可考虑：

- 在关于或帮助页面增加“免按键语音控制”说明；
- 引导用户打开系统“语音控制”；
- 提供推荐命令名称和快捷指令配置示例；
- 明确说明该功能由 macOS 管理麦克风和识别，不由无线麦保存语音。

在没有 Apple 公开配置 API 的情况下，不自动修改用户的辅助功能和语音控制命令。

### 阶段 2：无线麦内置本地模式

只有系统方案无法满足时再进入开发。推荐流程：

持续采集低采样率音频 → 本地检测唤醒词 → 显示已唤醒状态 → 在限定时间内识别一句命令 → 映射到白名单动作 → 执行 → 返回待命

关键设计：

- 默认关闭，必须由用户主动启用；
- 唤醒词至少两个音节或多个字，避免单字误触发；
- 唤醒后播放提示音或显示明显状态；
- 命令窗口超时后自动关闭；
- 支持“停止监听”和菜单栏一键暂停；
- 原始音频不写磁盘、不上传、不进入日志；
- 只记录匿名的命令成功/失败计数时，也必须允许关闭；
- 删除、发送、购买、退出或运行脚本等高风险动作必须二次确认；
- 屏幕锁定、用户切换或休眠时停止监听，唤醒后由用户设置决定是否恢复。

## 真机验收标准

阶段 0 至少验证：

- macOS 15 Apple Silicon；
- 中文命令和实际使用的麦克风；
- “打开 Codex”连续执行 50 次的成功率；
- 两小时办公环境中没有不可接受的误触发；
- 音乐、视频会议和扬声器播放期间的误触发情况；
- 暂停和恢复监听是否可靠；
- Codex 打开后输入框是否仍由现有功能正确聚焦。

如果开发阶段 2，还必须验证：

- 空闲 CPU、内存和耗电；
- 麦克风断开和重新接入；
- 睡眠、唤醒、锁屏和用户切换；
- 权限拒绝、撤销和重新授权；
- 离线状态；
- 中文、英文 App 名称和相似命令；
- 不保存原始音频，日志中不存在识别文本或敏感语音内容。

## 最终决策

**保留“免按键持续语音控制”TODO，并判定为可实现。第一选择不是新造硬件或立即开发持续识别，而是先验证 macOS 15 自带“语音控制”是否已经满足需求。**

只有系统方案的准确率、命令配置或产品体验确实不足时，才开发无线麦内置的“本地唤醒词 + 短时白名单命令识别”。RC003 在完成主动 `MIC_OPEN` 和 `MIC_EXTEND` 真机验证前，不进入正式持续收音方案。
