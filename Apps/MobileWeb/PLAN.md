# Remote Mic Mobile Web 完整实施计划

## 1. 文档状态

- 状态：第一版功能、生产部署和自动化验收已完成；真实 iPhone/Android 与黑客松现场网络验收待执行。
- 目标：提供无需安装 iOS App、使用手机浏览器扫码即可连接 Mac 的网页版遥控器。
- 主要场景：作品提前提交后，在黑客松现场由评委或观众直接体验方向键、常用控制键和按住说话。
- 目录决定：网页版放在 `Apps/MobileWeb/`，与 `Apps/RemoteMicIOS/` 并列。仓库现有目录使用大写 `Apps`，不新增仅大小写不同的 `apps` 目录。
- 公开边界：本文件只描述可公开的架构与流程，不记录真实域名、VPS 厂商、IP、SSH 信息、证书、Token 或其他部署凭据。
- 私有边界：真实部署资料只保存在 `.private/`、本机安全存储或独立私有基础设施仓库中；`.private/` 必须被 Git 忽略。

## 2. 产品目标

第一版必须实现以下完整体验：

1. Mac 用户在无线麦 App 中主动开启“连接网页版”。
2. Mac 主动建立到公网服务的加密出站连接，不要求用户配置路由器、端口转发或局域网地址。
3. Mac 显示一个短时有效的二维码和连接状态。
4. 手机使用 Safari 或 Chrome 扫码打开 HTTPS 页面，无需账号、TestFlight 或安装描述文件。
5. 手机与 Mac 显示同一校验码，Mac 用户明确允许后才能发送指令。
6. 网页提供与 iOS 遥控器一致的核心按钮，并显示 Mac 端的自定义按键标题。
7. 用户按住网页语音键时才申请或启用麦克风；松开、页面失焦、网络断开或会话终止时立即停止。
8. 音频进入 Mac 现有的虚拟麦克风链路，不在服务器或浏览器中持久化。

第一版的成功标准是“扫码后稳定完成一次真实遥控和语音输入演示”，而不是取代原生 iOS App。

## 3. 非目标

第一版不实现：

- 用户注册、登录、找回账号或跨设备同步；
- 多台 Mac 的云端设备列表和远程管理；
- 浏览器后台常驻、锁屏继续录音或系统级快捷入口；
- 与原生 App 等价的触觉反馈；
- 任意键盘数据、脚本、Shell 命令或文件传输；
- 语音识别、语音内容分析、录音保存或云端转写；
- 全球多区域中继、自动扩缩容或高并发商业化架构；
- 在第一版中承诺服务器无法读取数据的端到端加密；
- 替换现有 iOS Nearby/Bonjour 连接。网页版作为独立入口，与原生 iOS App 并存。

## 4. 推荐架构

```text
手机浏览器
  ├─ HTTPS：加载静态网页
  └─ WSS：加入一次性遥控会话
             │
             ▼
       公网会话中继服务
             ▲
             │ WSS 出站长连接
             │
          macOS App
             │
             ├─ 复用现有按键映射与 KeyboardInjector
             └─ 复用现有 VirtualAudioOutput
```

### 4.1 选择 WebSocket 中继的理由

- 手机和 Mac 可以位于不同网络；
- 不依赖 Bonjour、局域网 IP、路由器配置或会场 Wi-Fi 允许设备互访；
- Mac 只发起出站连接，不开放公网监听端口；
- 浏览器原生支持 HTTPS、WebSocket 和麦克风采集；
- 控制消息和 16kHz 单声道音频所需带宽较低；
- 第一版比原生 WebRTC 集成更容易调试和验收。

### 4.2 为什么第一版不使用纯局域网网页

- 浏览器不能复用当前 iOS 的 `NWBrowser` Bonjour 自动发现；
- 手机通过普通 HTTP 访问 Mac 时，浏览器通常不会把页面视为麦克风可用的安全上下文；
- 给每台 Mac 自动签发并维护浏览器信任的本地 HTTPS 证书会显著增加安装摩擦；
- 会场访客 Wi-Fi 经常启用客户端隔离，即使手机和 Mac 连接同一网络也可能无法互访。

### 4.3 为什么第一版不使用 WebRTC

WebRTC 的点对点链路和内置加密适合长期产品，但第一版需要在 macOS 端引入并维护 WebRTC 实现，还要处理信令、ICE、STUN、TURN、音频编解码和连接回退。第一版先使用可控的 WSS 中继完成体验验证；产品化阶段再根据隐私、延迟和运营成本决定是否迁移。

## 5. 组件边界

### 5.1 手机网页

职责：

- 解析二维码中的一次性会话信息；
- 展示连接、等待允许、已连接、错误和已结束状态；
- 渲染移动端单屏遥控器；
- 只发送协议白名单内的按键 ID；
- 在明确的按住手势后申请麦克风权限；
- 把麦克风转换为协议要求的单声道音频帧；
- 在所有结束路径停止音轨、释放音频节点并发送 `voiceStop`；
- 页面隐藏或离开前台时立即结束当前语音会话；
- 不把语音、配对令牌或会话内容写入 Local Storage、IndexedDB、Service Worker Cache 或分析 SDK。

### 5.2 公网中继服务

职责：

- 接受 Mac 与网页的 WSS 连接；
- 创建、加入和销毁一次性会话；
- 确保一个会话最多有一个 Mac 端和一个已批准的网页端；
- 在批准前只允许握手和校验消息；
- 批准后转发白名单控制消息和受限大小的音频帧；
- 对连接数、消息频率、单帧大小、会话时长和失败次数实施限制；
- 会话结束后立即清理内存状态；
- 提供不含业务载荷的健康检查和运行指标；
- 不记录按键内容、音频载荷、配对密钥或完整二维码 URL。

中继服务不负责：

- 执行 Mac 操作；
- 解析语音内容；
- 保存用户历史；
- 接收任意目标地址或充当通用代理；
- 向 Mac 下发协议之外的命令。

### 5.3 macOS App

职责：

- 只有用户主动开启网页版连接时才连接公网服务；
- 创建一次性会话并展示二维码；
- 显示校验码、网页设备信息和允许/拒绝提示；
- 将批准后的网页按键映射到现有 `RemoteButton` 白名单；
- 复用现有按键配置、辅助功能检查和使用次数统计；
- 将网页语音开始、音频帧和停止事件接入现有手机语音入口；
- 在 App 退出、用户关闭连接、网络失败或超时时停止语音并销毁会话；
- 保持现有原生 iOS Nearby 连接行为不变。

## 7. 会话与配对流程

### 7.1 创建会话

1. 用户在 Mac 点击“连接网页版”。
2. Mac 通过 WSS 向中继申请新会话。
3. 中继生成不可预测的会话 ID、一次性加入令牌和过期时间。
4. Mac 收到加入 URL 后生成二维码。
5. 未加入会话应在短时间内自动过期；过期时间做成服务端配置，不由客户端自行决定。

### 7.2 网页加入

1. 手机扫码打开 HTTPS 页面。
2. 页面建立 WSS 并提交一次性加入信息。
3. 中继把网页的有限展示信息发送给 Mac，例如浏览器类型和用户自选设备名称；不采集硬件指纹。
4. 双方基于当前会话生成并显示相同短校验码。
5. Mac 用户选择允许或拒绝。
6. 只有允许后，中继才进入可转发控制和音频的状态。

### 7.3 会话结束

以下任一条件发生时必须结束会话并停止语音：

- Mac 用户主动断开；
- 网页主动退出；
- 任一端网络连接关闭；
- 心跳超时；
- 会话达到最长时长；
- 同一会话出现非法消息、超限或认证失败；
- Mac App 退出、睡眠或切换用户；
- 网页进入后台时正在发送语音。

第一版默认采用“每次扫码、每次批准”的临时信任模式，不复用 iOS App 的长期设备信任。这样更适合评委或观众使用自己的手机体验。

## 8. 协议计划

### 8.1 版本

- 每条握手消息必须包含协议主版本；
- 主版本不兼容时直接拒绝，并向两端显示可理解的升级提示；
- 中继只路由已知版本，不对未知消息做透明转发；
- Web 协议独立版本化，不改变现有 Nearby 原始 TCP 协议。

### 8.2 控制消息

首版只允许以下类型：

```text
sessionCreate
sessionCreated
sessionJoin
sessionPendingApproval
sessionApprove
sessionDeny
sessionReady
buttonTitles
command
voiceStart
voiceStop
audio
heartbeat
error
sessionClose
```

`command` 只接受 Mac 已定义的 `RemoteButton` 白名单值。网页不能发送快捷键组合、应用路径、URL、Shell、AppleScript 或任意文本，由 Mac 根据本地配置决定实际动作。

### 8.3 音频消息

第一版目标格式：

- 16kHz；
- 16-bit；
- 单声道；
- 小端 PCM；
- 20–30ms 左右的短帧；
- WebSocket 二进制帧优先，避免 Base64 额外体积和编码开销；
- 每帧带会话内递增序号，便于检测乱序、丢帧和重复帧；
- 不做无限缓冲，过期音频直接丢弃，避免网络恢复后播放陈旧语音。

如果 Safari 音频采集到 16kHz PCM 的稳定性不满足要求，再评估 AudioWorklet 兼容策略或 Opus；不能在没有真机数据前同时引入多个编码路径。

## 9. 网页 UI 与交互

### 9.1 页面状态

- 加载会话；
- 等待 Mac；
- 等待批准并显示校验码；
- 已连接；
- 麦克风授权提示；
- 麦克风工作中；
- 可恢复网络错误；
- 会话过期、拒绝或结束。

### 9.2 遥控布局

- 复用 iOS 遥控器的核心信息层级和视觉语言，但不直接复制 SwiftUI 实现；
- 包含关机、方向、确定、返回、主页、菜单、TV、音量和按住说话；
- 中间六键顺序必须遵守仓库 `AGENTS.md` 的固定产品布局约束；
- Mac 端存在非默认按键配置时，在对应按钮内显示简短动作标题；
- 页面优先适配 iPhone Safari 的竖屏单屏体验，同时保证常见 Android Chrome 可操作；
- 不依赖 hover；触摸目标满足移动端可访问尺寸；
- 使用明确的按压视觉状态代替原生震动反馈；
- 第一版不要求“添加到主屏幕”，普通浏览器页面即可完成体验。

### 9.3 按住说话

- 只有用户真实按下语音按钮后才请求麦克风权限；
- 按下先发送 `voiceStart`，Mac 确认可用后再进入工作状态；
- 松开、触摸取消、指针离开、页面隐藏、连接错误时都执行幂等的 `voiceStop`；
- 页面持续显示正在使用麦克风；
- 拒绝权限后提供浏览器设置指引，不重复弹出无效请求；
- 不承诺锁屏、切到其他 App 或浏览器后台时继续录音。

## 11. 安全模型

### 11.1 第一版保护

- 全部公网通信使用 HTTPS/WSS；
- TLS 证书必须由浏览器和系统信任；
- 加入令牌使用密码学安全随机数，短时有效且使用后失效；
- 校验码和 Mac 端人工批准共同防止误连；
- 中继必须验证网页 Origin；
- 限制每个来源的连接、创建会话、加入失败和消息速率；
- 严格校验 JSON 结构、消息类型、字符串长度、音频帧大小和状态转换；
- 中继绑定到本机回环或私有容器网络，只通过受控反向代理或隧道公开；
- 不把现有 VPS 上的数据库、缓存、管理面板或内部服务暴露给公网；
- 网页设置严格 CSP、禁止第三方脚本、禁止不必要的分析 SDK；
- 日志只记录时间、匿名会话短标识、状态码、字节数、延迟和错误类别。

### 11.2 加密表述

第一版 WSS 是传输加密，不是服务器不可见的端到端加密。公开说明只能承诺：

> 按键和语音通过加密连接实时传输，仅用于当前会话，不保存语音内容。

在迁移到 WebRTC 或加入应用层端到端加密之前，不得使用“服务器无法读取”“零知识”或“端到端加密”等表述。

### 11.3 后续端到端加密

公开长期运行前重新评估：

- WebRTC DataChannel + 音频轨道；
- 或基于浏览器 Web Crypto 与 macOS CryptoKit 可共同实现的会话加密；
- 中继只看到连接元数据和密文；
- 密钥只存在于当前手机和 Mac 会话中；
- TURN 或其他中继仍不能解密业务内容。

该增强不能以自研加密算法替代标准协议，也不能为了兼容现有 Nearby 的 ChaChaPoly 封装而强迫浏览器使用未经审计的实现。

## 12. 隐私与数据处理

第一版不建立用户数据库。服务端仅保留当前连接所需的内存状态：

- 会话 ID；
- 两端连接引用；
- 批准状态；
- 创建、最后活动和过期时间；
- 限流计数；
- 必要的协议版本。

明确禁止持久化：

- 原始或编码后的语音；
- 按键明细；
- 自定义快捷键标题；
- 二维码完整 URL 和加入令牌；
- 可用于长期跟踪手机的浏览器指纹；
- Mac 硬件序列号、Apple ID 或外设标识。

部署前需要检查反向代理访问日志、应用异常日志和监控平台，确保它们不会自动记录 URL 中的敏感参数或 WebSocket 业务载荷。

## 13. 私有配置与不开源边界

以下内容不得进入 Git：

- 真实 Web Origin 和 WSS Endpoint；
- VPS 厂商、IP、区域、SSH 用户和端口；
- SSH 私钥；
- DNS、隧道、CDN 或证书服务 Token；
- 生产环境变量；
- 反向代理中的真实主机映射；
- 部署密钥、CI Secret 和运维恢复资料。

推荐方式：

1. 开源仓库只包含变量名和脱敏模板；
2. 本地开发值放入已忽略的 `.env.*` 或 `.private/`；
3. 生产配置保存在 VPS 的受限权限文件、系统凭据存储或独立私有基础设施仓库；
4. 发布构建通过私有配置注入公网服务地址，不在 Swift 源码写死；
5. CI 如放在公开仓库，只能引用 Secret 名称，不能输出值；若工作流本身会暴露基础设施拓扑，部署工作流也放入私有仓库。

需要明确：公网域名上线后会出现在浏览器地址栏、DNS 和网络请求中，无法成为真正秘密。本计划的目标是“不把部署资料提交到开源仓库”，而不是尝试隐藏用户必须访问的公网地址。VPS IP、账号和凭据仍应通过代理、隧道和私有配置保护。

## 14. VPS 部署原则

部署必须与 VPS 上已有服务隔离：

- 使用独立目录、独立进程或独立 Compose Project；
- 不复用已有应用的数据库、缓存、密钥或内部网络；
- 中继进程只监听回环地址或私有容器网络；
- 通过现有安全入口或独立反向代理路由公开 HTTPS/WSS；
- 设置最小权限用户、只读文件系统能力、资源限制和自动重启；
- 发布前先检查端口占用和现有服务健康，不覆盖已有配置；
- 更新只重启 Mobile Web 相关服务；
- 禁止执行会删除其他服务数据卷、镜像、网络或配置的全局清理命令；
- 提供独立健康检查、回滚版本和日志保留策略；
- 音频业务载荷不得进入反向代理和容器日志。

## 15. 可观测性

允许采集：

- 当前连接数；
- 成功创建、加入、批准和关闭的会话数量；
- 匿名化错误类别；
- 控制消息和音频字节总量；
- 端到端往返延迟分布；
- 会话持续时间分布；
- 服务 CPU、内存、重启次数和 WebSocket 异常关闭码。

禁止采集：

- 音频内容；
- 具体按键序列；
- 完整 IP 的长期用户画像；
- 完整 User-Agent 与其他字段组合形成的浏览器指纹；
- 完整会话令牌。

日志中的会话标识必须截断或重新生成，不能用真实加入令牌。

## 16. 实施阶段

当前进度：阶段 1–4 已完成并通过自动化与公网协议验收；阶段 0 中的真实 iPhone Safari 长时间音频测试、实际公网延迟测量，以及阶段 5 的多手机和现场网络演练仍需实体设备完成。

### 阶段 0：协议与技术验证

- 确定 Web 技术栈和 relay 运行时；
- 在 iPhone Safari 真机验证麦克风授权、AudioWorklet/采样转换和 WSS 二进制发送；
- 在 macOS 原型中验证 `URLSessionWebSocketTask` 或选定客户端能稳定收发控制和音频帧；
- 测量公网 VPS 往返延迟；
- 冻结协议 v1、帧大小和状态机。

退出条件：连续传送 10 分钟测试音频不出现无限积压，页面后台或断线能够停止发送。

### 阶段 1：中继与扫码配对

- 实现会话创建、加入、批准、拒绝、心跳、超时和销毁；
- 增加消息白名单、限流和帧大小限制；
- Mac 显示二维码和校验码；
- 网页显示等待和批准状态；
- 暂不发送真实按键和音频。

退出条件：不同网络下能够反复完成扫码、校验、允许、拒绝和超时，无会话串线。

### 阶段 2：按键遥控

- 完成移动端遥控器 UI；
- 接入白名单按键；
- 同步 Mac 自定义按键标题；
- 复用辅助功能检查和本地使用量统计；
- 验证长按、误触和重复消息策略。

退出条件：连续点击 500 次无串会话、非法命令、明显丢失或重复执行。

### 阶段 3：按住说话

- 完成浏览器麦克风授权；
- 转换并发送 16kHz 单声道音频帧；
- 接入 Mac 现有手机语音和虚拟麦克风链路；
- 处理松手、页面隐藏、网络断开和 Mac 拒绝语音；
- 增加延迟和丢帧观测。

退出条件：按住后目标时间内开始输出，松开后立即停止，连续 10 分钟无累积延迟，服务端日志不含音频载荷。

### 阶段 4：部署与安全加固

- 部署独立中继服务和静态网页；
- 配置可信 HTTPS/WSS、Origin 校验、CSP、限流和健康检查；
- 验证部署不会改变 VPS 既有服务；
- 完成回滚演练和配置备份；
- 执行仓库敏感信息扫描。

退出条件：生产域名可用，VPS 既有服务健康，公开仓库没有真实基础设施信息或凭据。

### 阶段 5：黑客松演示验收

- 使用实际演示 Mac 和至少两台不同手机完整走通；
- 覆盖同一 Wi-Fi、手机蜂窝网络、Mac 使用其他网络三种组合；
- 首次扫码到可点击控制的时间稳定可接受；
- 现场演示账号、二维码和服务不依赖开发工具；
- 准备服务不可用时的降级说明和原生 iOS/TestFlight 备用录像；
- 在正式演示前冻结版本，只修复阻断性问题。

## 17. 验收标准

### 功能

- 手机无需安装 App 即可打开页面；
- 未经 Mac 允许不能执行任何按键或发送音频；
- 所有核心按钮按 Mac 本地配置执行；
- 自定义按键标题能够同步；
- 语音通过现有虚拟音频设备有效输出；
- 会话关闭后旧二维码不能重新加入。

### 性能

- 控制按键在正常公网环境中无明显不可接受延迟；
- 语音开始时间、停止时间和连续使用延迟在真机中有明确测量结果；
- 网络抖动时不无限缓存旧音频；
- 单个演示会话不造成 VPS CPU、内存或带宽异常增长。

### 安全与隐私

- 中继只接受协议白名单消息；
- 无法通过网页提交任意快捷键、路径、脚本或目标地址；
- 会话令牌有过期和单次使用限制；
- 服务端、反向代理和浏览器存储中没有语音内容；
- Git 历史和构建日志中没有域名部署档案、VPS 信息或凭据；
- 公开隐私描述与实际 WSS 传输模型一致，不误称端到端加密。

### 兼容性

- 当前主流 iPhone Safari 真机；
- 至少一种主流 Android Chrome 真机；
- macOS App 当前最低支持系统；
- 页面旋转、锁屏、切后台和恢复后的状态明确且不会残留收音。

## 18. 风险与应对

### Safari 音频采集差异

风险：采样率、AudioWorklet、权限和页面生命周期与桌面浏览器不同。

应对：阶段 0 先做真机技术验证；只保留一条经过验证的音频路径，不靠模拟器结论进入实现。

### 公网延迟或丢包

风险：PCM 通过中继可能抖动，造成首字延迟或陈旧音频积压。

应对：小帧、序号、有限队列、过期丢弃；先测实际 VPS 到现场网络延迟，再决定是否需要 Opus 或 WebRTC。

### 会话被猜测或滥用

风险：公开服务可能遭到扫描、暴力加入或大帧攻击。

应对：高熵一次性令牌、短 TTL、Mac 人工批准、Origin 校验、严格消息大小、速率限制和连接上限。

### VPS 现有服务受影响

风险：端口、反向代理、容器网络、重启或资源竞争影响同机业务。

应对：独立部署单元、回环绑定、资源限制、窄范围更新、部署前后健康检查和可回滚版本。

### 域名或基础设施信息进入开源仓库

风险：源码、配置样例、测试快照、CI 输出或文档泄漏真实部署信息。

应对：私有部署档案、占位符模板、提交前 `git grep` 和敏感信息扫描；部署工作流如暴露拓扑则移到私有仓库。

### 隐私宣传超过实际能力

风险：WSS 被错误宣传为服务器不可见的端到端加密。

应对：第一版只声明传输加密和不保存；完成 WebRTC 或应用层端到端加密后再更新文案。

## 19. 发布与回滚

- Web、relay 和 Mac 协议版本必须可独立识别；
- relay 至少同时兼容当前生产版本和一个待发布版本，避免网页先更新导致旧 Mac 立即失效；
- 静态网页采用可回退的版本目录或不可变构建产物；
- relay 发布前保留上一稳定镜像或二进制；
- 数据仅在内存中，因此回滚不能依赖迁移用户数据库；
- 演示前记录经过验证的 Web 构建、relay 构建和 Mac App 版本；
- 出现严重问题时可以在服务端关闭新会话创建，不影响现有蓝牙和 Nearby 功能。

## 20. 已确认的实现决策

1. Web 前端使用 React + Vite + TypeScript，relay 使用 Node.js `http` + `ws`，不建立数据库。
2. 第一版以 iPhone Safari 为主要目标，Android Chrome 保留兼容能力并等待真机验收。
3. 未加入会话默认 5 分钟过期，已批准会话最长 2 小时；服务端仍是最终裁决方。
4. Nearby 与 Web 可以同时保持连接，但同一时间只允许一个移动端语音来源占用虚拟麦克风链路。
5. 公网 Relay URL 通过私有构建环境注入 App 的 `Info.plist`，公开 Swift 源码不包含生产地址。
6. 网页复用现有铝质背景和遥控器视觉语言，不改变仓库的 Logo 与 App Icon 品牌许可。
7. 第一版只宣传 HTTPS/WSS 传输加密、临时会话和不保存语音内容，不宣传端到端加密。

真实手机、虚拟麦克风听感和现场网络演练仍是发布黑客松演示前的必要人工验收，不能由桌面浏览器或协议测试替代。
